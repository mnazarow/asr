# Программный интерфейс

HTTP-интерфейс покрывает всё, что умеет веб-интерфейс: он сам построен поверх этого же API. Обмен в JSON, загрузка файлов — `multipart/form-data`, события — по WebSocket.

Живой справочник по адресу `/api/reference` собирается сервером из схемы OpenAPI и работает без интернета. Машинно-читаемая схема — `/api/openapi.json`.

Эта глава — введение: как устроен обмен и как решаются типовые задачи. Полный перечень маршрутов со всеми параметрами, правами доступа и настоящими примерами ответов вынесен в отдельный документ — «ASR Hub — программный интерфейс». Он собирается с работающего сервера командой `bash docs/build-api.sh`, поэтому не может разойтись с тем, что сервер отдаёт на самом деле.

## Аутентификация

Ключ передаётся одним из трёх способов — все три работают везде, включая оба WebSocket:

```bash
curl -H "X-API-Key: ah_ваш_ключ" ...                     # рекомендуемый
curl -H "Authorization: Bearer ah_ваш_ключ" ...
curl "http://сервер:8080/api/jobs?api_key=ah_ваш_ключ"   # только для WebSocket и ссылок
```

Третий способ оставлен для случаев, когда заголовок задать негде (адрес WebSocket, ссылка на скачивание в браузере). ⚠️ Ключ в адресе попадает в журналы прокси — в остальных случаях пользуйтесь заголовком.

Роли ключей:

| Роль | Права |
|---|---|
| `readonly` | чтение: списки, карточки, выгрузка результатов, аналитика |
| `user` | плюс создание, отмена и повтор заданий |
| `admin` | плюс настройки, ключи, обслуживание, управление очередью |

Создание ключа:

```bash
curl -X POST http://сервер:8080/api/keys \
  -H "X-API-Key: ah_ключ_администратора" -H "Content-Type: application/json" \
  -d '{"name": "интеграция CRM", "role": "user", "rate_limit": 600}'
```

Полное значение ключа возвращается один раз при создании — дальше видны только имя и первые символы плюс поле `key_id` (шестнадцать символов), которым ключ отзывается: `DELETE /api/keys/{key_id}`. Аутентификацию можно отключить целиком (`auth_enabled: false`), но только в доверенной сети.

### Что видит ключ

Разграничение сквозное: всё, кроме роли `admin`, работает только со своими заданиями. Это касается не только списка заданий, но и всего, что о них рассказывает:

| Где | Что видит не-администратор |
|---|---|
| `GET /api/jobs`, `GET /api/queue` | только свои задания |
| `GET /api/jobs/{id}` и всё под ним | своё; чужое и **задание без владельца** — 403 |
| `GET /api/events` | события своих заданий плюс общие о состоянии очереди. Создание и отзыв ключей, изменение настроек, загрузка моделей — только администратору |
| `GET /api/system` | сведения об оборудовании и версии. Раскладка файловой системы, путь к базе и файл конфигурации — только администратору |
| `GET /api/analytics` | сводки по своим заданиям во всех разрезах, включая языки и движки |
| События по WebSocket | события своих заданий; общие о состоянии очереди приходят всем |

Задание без владельца считается чужим для всех, кроме администратора: такие записи создают клиент командной строки и ключ, созданный с пустым именем.

### Подразделения

Трёх ролей хватало, чтобы ответить на вопрос «что можно делать», но не на вопрос «чьё это». Область видимости кончалась на владельце: два бухгалтера с разными ключами не могли работать с общим набором заданий, а единственный способ дать им общий доступ — выдать обоим роль администратора вместе с настройками и ключами сервера.

Ключ можно отнести к подразделению — тогда «своё» означает «своё и коллег»:

```bash
curl -X POST http://сервер:8080/api/keys \
  -H "X-API-Key: ah_ключ_администратора" -H "Content-Type: application/json" \
  -d '{"name": "бухгалтер-1", "role": "user", "group": "бухгалтерия"}'
```

Ключи с одинаковым `group` видят задания друг друга во всём, что перечислено в таблице выше: список, карточка, выгрузка, аналитика, события. Ключ без `group` по-прежнему видит только своё. Отдел продаж не увидит ничего бухгалтерского, даже если запросит владельца явно: `GET /api/jobs?owner=бухгалтер-1` от чужого подразделения вернёт свои задания, а не запрошенные.

Подразделение — это не роль: `readonly` в бухгалтерии читает задания коллег, но по-прежнему не может ни поставить задание, ни отменить чужое.

### Квоты

Роли отвечали «что можно», но не «сколько». Один ключ занимал всю очередь и весь диск, и остановить это можно было только отключив его целиком. Квота задаётся при создании ключа и считается за **скользящие сутки** — она восстанавливается сама, без обнуления по расписанию:

```bash
curl -X POST http://сервер:8080/api/keys \
  -H "X-API-Key: ah_ключ_администратора" -H "Content-Type: application/json" \
  -d '{"name": "интеграция CRM", "role": "user",
       "quota_jobs_per_day": 500,
       "quota_audio_hours_per_day": 40,
       "quota_storage_gb": 20}'
```

| Поле | Что ограничивает | Ноль означает |
|---|---|---|
| `quota_jobs_per_day` | число заданий за сутки | без ограничения |
| `quota_audio_hours_per_day` | суммарную длительность принятого звука | без ограничения |
| `quota_storage_gb` | суммарный объём исходных файлов | без ограничения |

Отменённые и не удавшиеся задания в расход не идут. У ключа в подразделении квота общая на всё подразделение — иначе её обходили бы, заведя второй ключ. Администратор не ограничен: иначе обслуживание сервера упиралось бы в ту же стену, что и злоупотребление.

Учитывается и то, что принимается прямо сейчас, — иначе одна загрузка на сто часов проходила бы поверх любой квоты. Отказ приходит до приёма тела запроса:

```json
{
  "error": {
    "code": "quota_exceeded",
    "message": "Исчерпана квота: заданий в сутки. Использовано 501 из 500.",
    "hint": "Квота считается за последние сутки и восстанавливается сама. Увеличить её может администратор — полем quota_jobs_per_day у вашего ключа доступа. Текущий расход виден в GET /api/usage.",
    "retryable": true,
    "details": {"kind": "jobs", "used": 501, "limit": 500, "field": "quota_jobs_per_day"}
  }
}
```

Узнать расход **до** отказа — `GET /api/usage`. Без него о квоте узнавали только в момент отказа, уже после того, как файл загружен:

```bash
curl -H "X-API-Key: $КЛЮЧ" http://сервер:8080/api/usage
```

```json
{
  "owner": "интеграция CRM", "group": "", "scope": ["интеграция CRM"],
  "window": "последние сутки",
  "used":      {"jobs": 137, "audio_hours": 9.4, "storage_gb": 3.1},
  "limits":    {"jobs": 500, "audio_hours": 40,  "storage_gb": 20},
  "remaining": {"jobs": 363, "audio_hours": 30.6, "storage_gb": 16.9}
}
```

`null` в `limits` — значит, по этому измерению ограничения нет.

Предел размера загрузки проверяется по заголовку `Content-Length` до приёма тела. Запрос больше `max_upload_mb` получает `413` сразу, не занимая места во временном каталоге; для `POST /api/jobs/batch` предел умножается на `max_batch_files`.

## Задания

### Поставить файл в очередь

```
POST /api/jobs        Content-Type: multipart/form-data
```

| Поле | Тип | Описание |
|---|---|---|
| `file` | файл | аудио или видео, обязательно |
| `settings` | JSON-строка | параметры задания; всё, что не указано, берётся из настроек сервера |
| `priority` | число | 1–100, по умолчанию 50 |
| `group_id` | строка | объединить с другими заданиями в группу |
| `tags` | строка | метки через запятую, для фильтрации |
| `reference_text` | строка | эталонная расшифровка для расчёта WER |
| `webhook_url` | строка | адрес для уведомления о завершении |

```bash
curl -X POST http://сервер:8080/api/jobs \
  -H "X-API-Key: ключ" \
  -F "file=@совещание.mp3" \
  -F 'settings={"model":"gigaam-v3-e2e-rnnt","language":"ru","diarization_enabled":true,"output_formats":["txt","srt","json"]}' \
  -F "priority=70" -F "tags=совещания,отдел-продаж"
```

```json
{
  "id": "job_7f3a9c21",
  "status": "queued",
  "filename": "совещание.mp3",
  "media_duration_s": 3612.4,
  "model": "gigaam-v3-e2e-rnnt",
  "priority": 70,
  "created_at": 1756612800.12,
  "progress": 0.0,
```

### Список заданий

```
GET /api/jobs?status=completed&model=gigaam-v3-rnnt&limit=50&offset=0
```

| Параметр | Описание |
|---|---|
| `status` | `queued`, `running`, `completed`, `failed`, `cancelled`, `retry`, `paused`; `active` — все незавершённые; можно перечислить через запятую |
| `owner`, `model`, `group_id` | фильтры по значению |

| `order` | сортировка, например `created_at DESC`, `media_duration_s ASC` |

### Карточка задания

```
GET /api/jobs/{id}?with_segments=true
```

Возвращает всё: статус, прогресс, стадию, времена по этапам, параметры, метрики, текст, ленту событий и — по запросу — сегменты с таймкодами, говорящими и уверенностью.

Вместе с ними приходит полоса громкости: `waveform` — разобранные точки, `waveforms` — те же данные в виде массива JSON-строк (см. следующий раздел). На часовой записи это сотни килобайт, поэтому если карточка опрашивается часто, добавьте `with_waveform=false`.

### Полоса громкости

```
GET /api/jobs/{id}/waveform
GET /api/jobs/{id}/waveform?fmt=phone_asr
```

Огибающая записи: один замер на интервал, `amplitude` — **средний модуль отсчёта** на этом интервале. Величина безразмерная, от 0 до 1: тишина даёт около 0.001, обычная речь — 0.15…0.25. Это не пик и не децибелы; среднее по модулю выбрано потому, что пик реагирует на один щелчок и делает полосу нечитаемой, а глаз ждёт от «полоски громкости» именно среднего уровня.

Кривых может быть несколько. Стереозапись даёт по кривой на канал, монозапись с диаризацией — по кривой на говорящего (вне своих реплик у него нули, поэтому наложенные полосы читаются как диалог), в остальных случаях кривая одна с меткой `all`.

```json
{
  "id": "job_7f3a9c21",
  "interval_s": 1.0,
  "duration_s": 128.4,
  "curves": [
    {
      "audio_waveform": [{"time": 0.0, "amplitude": 0.000638},
                         {"time": 1.0, "amplitude": 0.015378}],
      "sample_rate": 16000,
      "speaker": 0,
      "label": "Оператор"
    }
  ]
}
```

Форма `fmt=phone_asr` отдаёт `{"waveforms": ["{\"audio_waveform\": …}", …]}` — **массив JSON-строк**, а не объектов, и без поля `label`. Так это поле устроено в phone_asr, и приёмники, написанные под него, читают ответ ASR Hub без единой правки. То же поле есть в карточке задания и, если включить параметр `webhook_waveform`, в теле уведомления о завершении.

Шаг задаётся параметром `waveform_interval_s` (по умолчанию 1 секунда), расчёт целиком отключается параметром `waveform_enabled`.

## События по WebSocket

Браузерный WebSocket не умеет отправлять заголовки, поэтому ключ пришлось бы писать в адрес — а он попадает в историю браузера, в журнал обратного прокси и в заголовок `Referer`. Вместо ключа берётся одноразовый билет: он живёт минуту, гасится при первом подключении и не открывает доступ к HTTP-маршрутам.

```javascript
// 1. Билет — обычным запросом с заголовком
const { ticket } = await fetch('/api/auth/ticket', {
  method: 'POST',
  headers: { 'X-API-Key': ключ },
}).then((r) => r.json());

// 2. Подключение по билету
const ws = new WebSocket(`ws://сервер:8080/ws?ticket=${encodeURIComponent(ticket)}`);

ws.onmessage = (event) => {
  // Поля события лежат на верхнем уровне сообщения, вложенного data нет.
  const message = JSON.parse(event.data);
  switch (message.type) {
    case 'job.progress':  console.log(message.id, message.stage, message.progress); break;
    case 'job.completed': console.log('готово', message.id, 'RTF', message.rtf); break;
    case 'job.failed':    console.error(message.error.message, message.error.hint); break;
  }
};

setInterval(() => ws.send('ping'), 30000);   // держим соединение живым
```

Сторонние клиенты — те, что умеют задавать заголовки или живут в закрытом контуре, — могут по-прежнему подключаться с ключом: `ws://сервер:8080/ws?api_key=$КЛЮЧ`.

**Типы событий**

| Событие | Когда приходит | Полезные поля |
|---|---|---|
| `hello` | сразу после подключения | `queue` — состояние очереди, `history` — последние 20 событий |
| `job.queued` | задание принято | `id`, `filename` |
| `job.started` | задание взято в работу | `id`, `filename` |
| `job.progress` | по ходу распознавания | `id`, `progress` (0…1), `stage` |
| `job.completed` | задание готово | `id`, `rtf` |
| `job.failed` | задание не удалось | `id`, `error` — объект с `code`, `message`, `hint` |
| `job.retry` | будет повтор после сбоя | `id`, `attempt`, `delay_s`, `error` |
| `job.cancelled` | задание отменено | `id` |
| `job.cached` | результат взят из кеша | `id`, `source` — задание, из которого взят результат |
| `queue.paused` | очередь приостановлена | — |
| `queue.resumed` | очередь возобновлена | — |
| `queue` | ответ на команду `status` | состояние очереди целиком |
| `pong` | ответ на команду `ping` | — |

В каждом сообщении есть `type` и `ts` — время события. Клиент может отправить серверу две команды: `ping` (ответ `pong`, чтобы соединение не закрыл прокси) и `status` (ответ `queue`).

## Распознавание на лету

Файл принимался целиком: чтобы получить первое слово, надо было дождаться конца записи. Для звонка, диктовки и субтитров это не годится. Маршрут `ws://сервер:8080/api/stream` принимает звук кусками и отдаёт текст по ходу.

Управление — текстовые сообщения JSON, звук — двоичные кадры. Ключ предъявляется так же, как на `/ws`: одноразовым билетом в параметре `ticket`, ключом в заголовке `X-API-Key`, заголовком `Authorization: Bearer` или параметром `api_key`. Поток — это работа, а не чтение, поэтому ключу с ролью `readonly` он закрыт (код закрытия `4403`), а выключенный параметром `stream_enabled` — всем (`4404`).

### Два способа работы, и разница между ними честная

| Режим | Когда | Задержка | Цена |
|---|---|---|---|
| `native` | движок держит состояние между кусками (Vosk) | доли секунды | звук распознаётся один раз |
| `window` | движок состояния не держит (Whisper, GigaAM) | размер окна | накопленный звук распознаётся заново каждое окно |

Гадать не приходится: сессия сообщает свой режим первым же сообщением. В режиме окна размер задаётся параметром `stream_window_s` (по умолчанию 4 секунды): меньше — чаще обновления и больше повторной работы.

### Обмен

```javascript
const { ticket } = await fetch('/api/auth/ticket', {
  method: 'POST', headers: { 'X-API-Key': ключ },
}).then((r) => r.json());

const ws = new WebSocket(`ws://сервер:8080/api/stream?ticket=${encodeURIComponent(ticket)}`);
ws.binaryType = 'arraybuffer';

ws.onopen = () => {
  // 1. Настройка: модель, язык, формат звука, размер окна.
  ws.send(JSON.stringify({ type: 'config', format: 'auto', stream_window_s: 3 }));
};

ws.onmessage = (event) => {
  const message = JSON.parse(event.data);
  switch (message.type) {
    case 'ready':   console.log('режим', message.mode, message.note); break;
    case 'partial': показатьЧерновик(message.text); break;   // будет уточнён
    case 'final':   дописатьВРасшифровку(message.text); break;
    case 'done':    console.log('всего', message.duration_s, 'с звука'); break;
    case 'error':   console.error(message.message, message.hint); break;
  }
};

// 2. Звук — двоичными кадрами, любого размера.
recorder.ondataavailable = (e) => ws.send(e.data);

// 3. Конец записи.
кнопкаСтоп.onclick = () => ws.send(JSON.stringify({ type: 'finish' }));
```

**Сообщения клиента**

| Сообщение | Что делает |
|---|---|
| `{"type": "config", ...}` | первое сообщение: модель, язык и прочие параметры задания плюс `format`. Необязательно — без него берутся серверные значения по умолчанию |
| двоичный кадр | кусок звука; размер любой, накопление считает сервер |
| `{"type": "finish"}` | конец записи: сервер досчитывает хвост, отдаёт `final` и `done`. Синонимы — `stop`, `eof` |
| `{"type": "ping"}` | ответ `{"type":"pong"}`, чтобы соединение не закрыл прокси |

**Сообщения сервера**

| Событие | Когда | Поля |
|---|---|---|
| `ready` | сразу после настройки | `mode` (`native`/`window`), `model`, `sample_rate`, `window_s`, `note` — человеческое описание режима |
| `partial` | гипотеза по ходу; будет уточнена | `text`, `start`, `end` |
| `final` | окончательный кусок текста | `text`, `start`, `end` |
| `done` | сессия закрыта | `duration_s`, `text` — весь текст целиком |
| `error` | отказ | `message`, `hint`, `code` |

`partial` — черновик: следующее сообщение того же вида заменяет предыдущее целиком. `final` — то, что уже не изменится, и его надо дописывать, а не заменять.

### Формат звука

| `format` | Что присылать |
|---|---|
| `pcm_s16le` (по умолчанию) | сырой звук: моно, 16 кГц, 16 бит со знаком. Ничего не кодируется — самый дешёвый путь |
| `auto` | любой контейнер, который понимает ffmpeg: WebM/Opus из `MediaRecorder`, Ogg, MP3. Приведением занимается один долгоживущий процесс ffmpeg на сессию |

⚠️ В режиме `auto` присылайте **один непрерывный поток**, а не отдельные файлы: `MediaRecorder` с `timeslice` даёт именно его, а вот склейка независимых `.webm` разорвёт разбор.

### Пределы и цена

Сессия длиннее часа прерывается сообщением `error`: поток без конца — это растущий буфер и занятая модель. Для длинных записей ставьте обычное задание — `POST /api/jobs`. Движок берётся из общего реестра короткой арендой на каждое распознавание, поэтому разговор не блокирует очередь файловых заданий, но и не ускоряет её.

В режиме окна накопленный звук распознаётся заново, поэтому цена выше, чем у обычного задания, — но она ограничена: хвост закрепляется примерно каждые полминуты и освобождается, и работа одного окна не зависит от того, сколько уже наговорено. Час диктовки не превращается в час, умноженный на число окон. Настоящий поток (Vosk) считает звук один раз и такой платы не требует вовсе.

Практический ориентир для окна: 3–5 секунд. Меньше — обновления чаще, но каждое стоит полного прохода модели; больше — дешевле, но текст появляется реже.

Готовый пример клиента с настоящим обменом — `examples/stream_microphone.py`; он умеет и микрофон, и «наговаривание» готового файла, чтобы поток можно было посмотреть без звуковой карты:

```bash
pip install websocket-client
python3 examples/stream_microphone.py --file запись.wav
```


## Приём разговоров по схеме phone_asr

Раздел нужен, чтобы не переписывать то, что уже работает. Приложение, которое сегодня отправляет разговоры в `phone_asr`, переключается на ASR Hub сменой адреса: путь, имена полей, код ответа и обратный вызов совпадают дословно.

Порядок отличается от `POST /api/jobs` и для телефонии подходит лучше: вы не загружаете файл, а сообщаете, где он лежит, и получаете ответ не в этом же запросе, а отдельным обращением на свой адрес. Запись появляется на файловом сервере АТС, разговор длится минуты — держать соединение открытым всё это время незачем.

Выключается параметром `phone_compat_enabled`.

### Отправить разговор

```bash
curl -X POST "http://сервер:8080/process-call?api_key=$КЛЮЧ" \
  -H "Content-Type: application/json" \
  -d '{
        "call_id": "4821",
        "base_url": "https://мойсервер.ru",
        "files": ["https://мойсервер.ru/rec/4821-оператор.wav",
                  "https://мойсервер.ru/rec/4821-абонент.wav"],
        "part": 1,
        "total_parts": 1,
        "swap_sides": false
      }'
```

```json
{
  "status": "accepted",
  "message": "Обработка звонка с ID 4821 добавлена в очередь. Результаты будут отправлены на https://мойсервер.ru/callback-endpoint.php."
}
```

Ответ — `202 Accepted`: «взято в работу», а не «готово».

| Поле | Что означает |
|---|---|
| `call_id` | ваш идентификатор разговора; возвращается в обратном вызове |
| `files` | один или два адреса. Один — запись целиком: стерео разведётся по каналам, моно уйдёт на диаризацию. Два — раздельные дорожки сторон, обе моно |
| `base_url` | адрес вашего приёмника. Схема дописывается, если её нет; завершающая косая черта снимается |
| `part`, `total_parts` | номер части и сколько их всего, если запись разрезана |
| `swap_sides` | поменять стороны местами: первая дорожка станет `SPEAKER_01` |

⚠️ Ключ доступа нужен, как и всюду. Если вызывающая сторона не умеет заголовки — `?api_key=...` в строке запроса.

### Что придёт обратно

`POST` на `{base_url}/callback-endpoint.php` (суффикс меняется параметром `phone_compat_callback_suffix`):

```json
{
  "call_id": "4821",
  "base_path": "[\"4821-оператор.wav\", \"4821-абонент.wav\"]",
  "part": 1,
  "total_parts": 1,
  "true_duration": 186.4,
  "sentiment": "neutral",
  "waveforms": ["{\"audio_waveform\": [{\"time\": 0.0, \"amplitude\": 0.27}], \"speaker\": 0}", "…"],
  "formatted_dialogue": [
    {"speaker": "SPEAKER_00", "dialogue": "Добрый день, компания «Вектор».", "time": 0.0, "time_end": 3.2}
  ],
  "transcription": "Добрый день, компания «Вектор». …",
  "status": "success",
  "error_message": null
}
```

Две особенности схемы сохранены нарочно, потому что принимающая сторона написана под них: `base_path` — **строка** с JSON внутри, а не список; `waveforms` — список **строк**, каждую надо разбирать отдельно. Поле `sentiment` в `phone_asr` объявлено, но нигде не вычисляется — здесь оно тоже всегда `neutral`.

Отказ приходит тем же обратным вызовом со `status: "failed"` и причиной в `error_message`. Молчание было бы худшим исходом: вы ответили `202` и ждёте результат, которого не будет.

⚠️ Если ваш приёмник стоит в локальной сети (обычное дело), включите `webhook_allow_internal` — иначе сервер откажется отправлять результат на внутренний адрес. Отказ придёт сразу, при приёме разговора, а не через минуту.

### Состояние разговоров

```bash
curl -H "X-API-Key: $КЛЮЧ" http://сервер:8080/statuses
```

```json
[{"call_id": "4821", "part": 1, "status": "success"}]
```

Состояния в словаре `phone_asr`: `pending`, `in_progress`, `success`, `failed`.

### Что при этом остаётся своим

Совместимость касается только краёв. Внутри это обычное задание ASR Hub: у него есть владелец, оно считается против квот, попадает в очередь и в кеш, видно в интерфейсе и в аналитике, к нему применяются все параметры сервера. То есть вы получаете и старый способ передачи, и всё, чего в `phone_asr` не было.

Те же маршруты доступны и под `/api` — `POST /api/process-call`, `GET /api/statuses`, — чтобы новые клиенты не выглядели исключением среди прочих.

## Формат ошибок

Все ошибки приходят в одном виде:

```json
{
  "detail": {
    "code": "out_of_memory",
    "message": "Недостаточно памяти на устройстве GPU.",
    "hint": "Уменьшите batch_size или выберите модель полегче. Задание будет повторено автоматически с меньшим пакетом.",
    "retryable": true,
    "context": {"device": "cuda:0", "requested": "11.2 ГБ"}
  }
}
```

`retryable` говорит, имеет ли смысл повторять запрос. `hint` — не украшение: это конкретное действие, которое чаще всего решает проблему.

| Код | HTTP | Повторять | Значение |
|---|---|---|---|
| `config_error` | 400 | нет | недопустимое значение параметра |
| `audio_error` | 400 | нет | файл нечитаем или без звуковой дорожки |
| `unsupported_feature` | 400 | нет | движок не умеет запрошенного |
| `auth_error` | 401 | нет | ключ отсутствует или недействителен |
| `forbidden` | 403 | нет | недостаточно прав |
| `gated_model` | 403 | нет | нужно принять условия у правообладателя весов |
| `job_not_found` | 404 | нет | нет такого задания |
| `model_not_found` | 404 | нет | нет такой модели (в ответе — похожие имена) |
| `job_cancelled` | 409 | нет | задание уже отменено |
| `file_too_large` | 413 | нет | превышен `max_upload_mb` |
| `audio_too_long` | 413 | нет | превышен `audio_max_duration_s` |
| `unsupported_format` | 415 | нет | расширение не поддерживается |
| `no_speech` | 422 | нет | речь не найдена |
| `queue_full` | 429 | да | очередь переполнена |
| `rate_limited` | 429 | да | превышен лимит частоты |
| `engine_error` | 500 | да | сбой внутри движка |
| `dependency_missing` | 503 | нет | не установлен пакет движка |
| `binary_missing` | 503 | нет | не найдена внешняя программа (обычно ffmpeg) |
| `hardware_error` | 503 | да | проблема с устройством или драйвером |
| `out_of_memory` | 503 | да | не хватило памяти |
| `model_not_downloaded` | 503 | да | веса не загружены |
| `model_load_error` | 503 | да | веса есть, но не грузятся |
| `job_timeout` | 504 | да | превышен `job_timeout_s` |
| `storage_error` | 507 | да | нет места на диске |

## Пример на Python

```python
import time
import requests

SERVER = "http://сервер:8080"
HEADERS = {"X-API-Key": "ah_ваш_ключ"}


def transcribe(path, **settings):
    """Отправляет файл, дожидается результата, возвращает субтитры."""
    import json
    with open(path, "rb") as fh:
        response = requests.post(
            f"{SERVER}/api/jobs", headers=HEADERS,
            files={"file": fh},
            data={"settings": json.dumps(settings or {"model": "gigaam-v3-e2e-rnnt"})},
            timeout=300)
    if response.status_code != 200:
        error = response.json()["detail"]
        raise RuntimeError(f"{error['code']}: {error['message']}\n{error.get('hint', '')}")

    job_id = response.json()["id"]
    while True:
        job = requests.get(f"{SERVER}/api/jobs/{job_id}", headers=HEADERS, timeout=30).json()
        if job["status"] == "completed":
            break
        if job["status"] == "failed":
            raise RuntimeError(job["error_message"])
        time.sleep(3)

    return requests.get(f"{SERVER}/api/jobs/{job_id}/download",
                        params={"fmt": "srt"}, headers=HEADERS, timeout=60).text


print(transcribe("совещание.mp3", model="gigaam-v3-e2e-rnnt", diarization_enabled=True))
```

Ожидание в цикле подходит для скрипта; в постоянно работающем сервисе используйте webhook или WebSocket, чтобы не опрашивать сервер впустую.
