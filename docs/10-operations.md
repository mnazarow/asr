# Эксплуатация

Раздел о том, что делать с системой после того, как она заработала: как её обслуживать, за чем следить, что резервировать и как не потерять данные.

## Служба

```bash
bash scripts/service.sh start
bash scripts/service.sh stop
bash scripts/service.sh restart
bash scripts/service.sh status
bash scripts/service.sh logs -n 200 -f
```

Под этими командами — systemd на Linux, launchd на macOS, NSSM или планировщик задач на Windows. Служба перезапускается при сбое и стартует при загрузке машины.

Штатный порядок перезапуска, чтобы не потерять работу:

```bash
curl -X POST http://127.0.0.1:8080/api/queue/pause -H "X-API-Key: ключ"
# дождаться, пока список выполняющихся опустеет
watch -n 5 'curl -s -H "X-API-Key: ключ" http://127.0.0.1:8080/api/queue | jq .running'
bash scripts/service.sh restart
```

Даже без этой предосторожности задания не теряются: оставшиеся в состоянии `running` возвращаются в очередь при следующем старте. Пауза лишь избавляет от повторного счёта.

## Конфигурация

Значения складываются слоями, каждый следующий перекрывает предыдущий:

```
умолчания каталога → автоопределение железа → config.yaml → переменные ASRHUB_* → параметры задания
```

Файл конфигурации создаётся при установке с комментарием к каждому параметру — около 1700 строк, читается как справочник. Пересоздать:

```bash
python3 -c "import sys; sys.path.insert(0,'server')
from asrhub.config import generate_example_config
print(generate_example_config())" > config.example.yaml
```

Переменные окружения удобны в контейнере и в systemd:

```bash
ASRHUB_PORT=9000
ASRHUB_DEVICE=cuda
ASRHUB_MAX_CONCURRENT_JOBS=3
ASRHUB_MODELS_DIR=/srv/models
ASRHUB_AUTH_ENABLED=true
ASRHUB_LOG_LEVEL=INFO
```

Изменения через `PUT /api/settings` действуют немедленно, но живут до перезапуска. Чтобы они пережили его, вызовите `POST /api/settings/save` — значения запишутся в `config.yaml`.

## Резервное копирование

| Что | Где | Насколько важно |
|---|---|---|
| База заданий | `<данные>/asrhub.db` | **критично** — вся история, метрики, ключи |
| Конфигурация | `config.yaml` | **критично** — восстанавливается вручную за час |
| Результаты | `<данные>/results/` | важно, если не выгружены наружу |
| Загруженные файлы | `<данные>/uploads/` | обычно не нужно |
| Веса моделей | `<данные>/models/` | **не нужно** — скачиваются заново |

Веса — это десятки гигабайт, которые бессмысленно резервировать: они воспроизводимы. База — единицы мегабайт, и она незаменима.

Копия базы делается на живом сервере, без остановки:

```bash
sqlite3 /var/lib/asrhub/asrhub.db ".backup '/резерв/asrhub-$(date +%F).db'"
```

⚠️ Не копируйте файл базы обычным `cp` на работающем сервере: включён режим WAL, и рядом лежат `-wal` и `-shm`, без которых копия окажется в несогласованном состоянии. `.backup` делает всё правильно.

Ежедневная задача:

```bash
# /etc/cron.d/asrhub-backup
0 3 * * * asrhub sqlite3 /var/lib/asrhub/asrhub.db \
  ".backup '/резерв/asrhub-$(date +\%F).db'" && \
  find /резерв -name 'asrhub-*.db' -mtime +30 -delete
```

## Очистка

Дисковое пространство расходуют три вещи: загруженные файлы, результаты и веса моделей.

```bash
curl -X POST http://127.0.0.1:8080/api/maintenance/cleanup -H "X-API-Key: ключ"
```

Удаляются задания, завершённые раньше чем `result_retention_days` назад (по умолчанию 30 дней), метрики старше 180 дней и события старше 90. Настройки хранения:

```yaml
result_retention_days: 30      # 0 — хранить вечно
delete_source_after: true      # удалять загруженный файл сразу после обработки
```

`delete_source_after: true` — правильное значение для большинства случаев: исходники обычно есть у отправителя, а на сервере они только занимают место. Оставьте `false`, только если сервер — единственное место, где записи хранятся.

Веса неиспользуемых моделей:

```bash
bash scripts/models.sh disk                     # сколько чем занято
bash scripts/models.sh remove whisper-large-v2  # удалить конкретную
```

## Управление памятью

```yaml
model_cache_size: 2            # сколько моделей держать загруженными
model_idle_unload_s: 900       # выгрузить после 15 минут простоя
gpu_memory_fraction: 0.9       # доля видеопамяти, доступная процессу
```

Загрузка модели занимает от 5 до 40 секунд. При потоке однородных заданий держать модель в памяти выгодно — иначе загрузка съест больше времени, чем распознавание. Показатель `model_load_share` в разделе «Эффективность» показывает, насколько это актуально именно у вас: если он выше 0,2, увеличьте кеш или время выгрузки.

При разнородном потоке и ограниченной памяти, наоборот, полезно уменьшить `model_cache_size` до 1: две большие модели одновременно могут не поместиться, и вы получите ошибки нехватки памяти вместо небольшой задержки.

## Мониторинг

Минимальный набор проверок:

```bash
curl -sf http://127.0.0.1:8080/api/health || echo "сервер не отвечает"
```

Что стоит выводить на график:

| Метрика | Тревожный признак |
|---|---|
| `asrhub_jobs_total{status="queued"}` | устойчивый рост — не хватает мощности |
| `asrhub_disk_free_gb` | приближение к `disk_min_free_gb` |
| `asrhub_rtf_p95` | рост при неизменной нагрузке — деградация железа или троттлинг |
| `asrhub_success_rate` | падение — смотрите раздел «Ошибки» |
| `asrhub_gpu_percent` | устойчивые 100 % — узкое место найдено |

Экспортер Prometheus включён по умолчанию (`metrics_enabled: true`), точка `/api/metrics` доступна без ключа: её закрывают на уровне прокси, если сервер смотрит в интернет.

Полноценный мониторинг — отдельный раздел [16. Мониторинг](16-monitoring.md): 63 метрики в семи форматах, пробы состояния, тревоги по порогам и готовые настройки для Prometheus, Grafana и Zabbix.

## Журналы

```bash
bash scripts/service.sh logs -n 500 -f
curl -H "X-API-Key: ключ" \
  "http://127.0.0.1:8080/api/logs?level=error&limit=100"
```

Файл журнала лежит в `<данные>/logs/asrhub.log` с ротацией. Уровень задаётся `log_level`; `DEBUG` включают на время разбора конкретной проблемы — он многословен.

⚠️ Параметр `log_transcript_text` по умолчанию **выключен**, и менять это не стоит. Включённый, он пишет распознанный текст в журнал — то есть содержание разговоров попадает в файл, который читают администраторы, забирает система сбора логов и хранит резервная копия. Для отладки достаточно карточки задания.

## Безопасность

Практический минимум:

1. **Аутентификация включена** (`auth_enabled: true`), ключи выданы поимённо. Ключ на каждую интеграцию — отозвать один, не трогая остальных.
2. **Роли по назначению.** Интеграции, которая только забирает результаты, нужен `readonly`.
3. **Сервер не смотрит в интернет напрямую.** HTTPS через прокси, VPN или SSH-туннель.
4. **Слушать localhost**, если доступ идёт через прокси на той же машине: `server_host: 127.0.0.1`.
5. **CORS закрыт** (`cors_origins: ""`), если браузерный доступ с других доменов не нужен.
6. **Отдельный системный пользователь** для службы, каталог данных с правами 0750.
7. **`delete_source_after: true`**, чтобы записи не накапливались.

Записи разговоров — чувствительные данные. Сервер распознавания хранит и загруженные файлы, и расшифровки; относитесь к нему как к хранилищу персональных данных, а не как к вычислительному узлу.

## Обновление

```bash
bash scripts/update.sh --check      # что изменится
bash scripts/update.sh              # обновить со снимком
bash scripts/update.sh --rollback   # вернуть предыдущую версию
```

Порядок для рабочего сервера:

1. Резервная копия базы (`.backup`).
2. `--check` — посмотреть, что меняется.
3. Пауза очереди, дождаться завершения текущих заданий.
4. Обновление.
5. `bash scripts/doctor.sh` и пробное задание.
6. Снять паузу.

Если после обновления что-то не так — `--rollback` возвращает код, конфигурацию и базу к состоянию до обновления.

## Настройка производительности

Пошагово, от самого действенного:

1. **Проверьте, что задействован ускоритель.** `GET /api/system` покажет устройство. Задание, случайно посчитанное на процессоре, идёт в 10–30 раз дольше. Это самая частая причина «медленно».
2. **Включите VAD.** Тишина, паузы и музыкальные заставки составляют в записях совещаний до трети длительности. Не подавать их в модель — бесплатное ускорение без потери качества.
3. **Подберите `batch_size`.** Увеличивайте, пока не упрётесь в память. На видеокарте 12 ГБ с large-моделью обычно 8–16.
4. **Возьмите модель полегче там, где она достаточна.** `gigaam-v3-ctc` быстрее `gigaam-v3-rnnt` в полтора-два раза, а разница в WER — меньше процентного пункта.
5. **Уменьшите `beam_size`.** С 5 до 1 — примерно вдвое быстрее; качество проседает заметно только на сложном звуке.
6. **Проверьте `compute_type`.** На видеокарте `float16` вместо `float32` — вдвое быстрее и вдвое меньше памяти при неразличимом качестве. На процессоре — `int8`.
7. **Держите модель в памяти** между заданиями, если поток однородный.

Подробные сценарии с цифрами — [12. Сценарии настройки](12-tuning.md).

## Ежедневные проверки

```bash
#!/usr/bin/env bash
# Утренняя сводка: живость, очередь, ошибки за сутки, место на диске.
СЕРВЕР=http://127.0.0.1:8080
КЛЮЧ=ah_ваш_ключ

curl -sf "${СЕРВЕР}/api/health" >/dev/null || { echo "СЕРВЕР НЕ ОТВЕЧАЕТ"; exit 1; }

curl -s -H "X-API-Key: ${КЛЮЧ}" "${СЕРВЕР}/api/queue" \
  | jq '{ожидают: .queued, выполняются: .running, воркеров: .workers}'

curl -s -H "X-API-Key: ${КЛЮЧ}" "${СЕРВЕР}/api/analytics/errors?period=day" \
  | jq '.by_code'

df -h /var/lib/asrhub | tail -1
```
