# Эксплуатация

Раздел о том, что делать с системой после того, как она заработала: как её обслуживать, за чем следить, что резервировать и как не потерять данные.

## Служба

```bash
bash scripts/service.sh start
bash scripts/service.sh stop
bash scripts/service.sh restart
bash scripts/service.sh status
bash scripts/service.sh logs -n 200 -f
```

Под этими командами — systemd на Linux, launchd на macOS, NSSM или планировщик задач на Windows. Служба перезапускается при сбое и стартует при загрузке машины.

Штатный порядок перезапуска, чтобы не потерять работу:

```bash
curl -X POST http://127.0.0.1:8080/api/queue/pause -H "X-API-Key: ключ"
# дождаться, пока список выполняющихся опустеет
watch -n 5 'curl -s -H "X-API-Key: ключ" http://127.0.0.1:8080/api/queue | jq .running'
bash scripts/service.sh restart
```

Даже без этой предосторожности задания не теряются: оставшиеся в состоянии `running` возвращаются в очередь при следующем старте. Пауза лишь избавляет от повторного счёта.

## Конфигурация

Значения складываются слоями, каждый следующий перекрывает предыдущий:

```
умолчания каталога → автоопределение железа → config.yaml → переменные ASRHUB_* → параметры задания
```

Файл конфигурации создаётся при установке с комментарием к каждому параметру — около 1700 строк, читается как справочник. Пересоздать:

```bash
python3 -c "import sys; sys.path.insert(0,'server')
from asrhub.config import generate_example_config
print(generate_example_config())" > config.example.yaml
```

Переменные окружения удобны в контейнере и в systemd:

```bash
ASRHUB_PORT=9000
ASRHUB_DEVICE=cuda
ASRHUB_MAX_CONCURRENT_JOBS=3
ASRHUB_MODELS_DIR=/srv/models
ASRHUB_AUTH_ENABLED=true
ASRHUB_LOG_LEVEL=INFO
```

Изменения через `PUT /api/settings` действуют немедленно, но живут до перезапуска. Чтобы они пережили его, вызовите `POST /api/settings/save` — значения запишутся в `config.yaml`.

## Резервное копирование

| Что | Где | Насколько важно |
|---|---|---|
| База заданий | `<данные>/asrhub.db` | **критично** — вся история, метрики, ключи |
| Конфигурация | `config.yaml` | **критично** — восстанавливается вручную за час |
| Результаты | `<данные>/results/` | важно, если не выгружены наружу |
| Загруженные файлы | `<данные>/uploads/` | обычно не нужно |
| Веса моделей | `<данные>/models/` | **не нужно** — скачиваются заново |

Веса — это десятки гигабайт, которые бессмысленно резервировать: они воспроизводимы. База — единицы мегабайт, и она незаменима.

Копия базы делается на живом сервере, без остановки:

```bash
sqlite3 /var/lib/asrhub/asrhub.db ".backup '/резерв/asrhub-$(date +%F).db'"
```

⚠️ Не копируйте файл базы обычным `cp` на работающем сервере: включён режим WAL, и рядом лежат `-wal` и `-shm`, без которых копия окажется в несогласованном состоянии. `.backup` делает всё правильно.

### Сервер делает копии сам

Ту же работу умеет и сам сервер — тогда ни `cron`, ни отдельная задача не нужны:

| Настройка | По умолчанию | Что задаёт |
|---|---|---|
| `backup_interval_hours` | `0` (не делать) | как часто снимать копию |
| `backup_keep` | `7` | сколько копий хранить; лишние удаляются, начиная со старых |
| `backup_dir` | пусто | куда складывать; пусто — `<данные>/backups` |

```yaml
backup_interval_hours: 24
backup_keep: 7
backup_dir: /mnt/backup/asrhub
```

Копия снимается тем же способом, что и вручную, — командой SQLite `.backup`. Отсчёт идёт от предыдущего раза, а не по календарю: отметка лежит в базе и переживает перезапуск, поэтому перезапуск сервера не приводит ни к пропущенной копии, ни к лишней.

Имя копии несёт дату, время и имя экземпляра (`asrhub-20260909-030000-server1_4821.db`): на общей базе серверов несколько, и без имени два одновременных захода выбирали один файл. Лишние копии удаляются **до** снятия новой, а не после: каталог обычно лежит на той же файловой системе, что и база, и при обратном порядке очередная копия не помещалась, старые не удалялись, и свежих копий не появлялось больше никогда.

⚠️ Каталог по умолчанию лежит рядом с базой. Это спасает от ошибочного удаления и порчи базы, но **не спасает от отказа диска** — а это самая частая причина, ради которой резервные копии и заводят. Укажите `backup_dir` на другом физическом диске или на сетевом хранилище.

Снять копию прямо сейчас и восстановиться из неё:

```bash
bash scripts/service.sh backup
bash scripts/service.sh restore --from /var/lib/asrhub/backups/asrhub-20260908-030000.db
```

Восстановление сначала проверяет копию (`PRAGMA integrity_check`) и только потом трогает рабочую базу: битый файл, обнаруженный после подмены, оставил бы вообще без базы — с двумя нерабочими файлами вместо одного. Служба на время восстановления останавливается, а прежняя база и её журнал сохраняются рядом с пометкой `before-restore-…`: восстановление не из той копии — обычная ошибка, и она должна быть обратимой. Удалите эти файлы, когда убедитесь, что всё на месте.

### Cron, если своё расписание удобнее

```bash
# /etc/cron.d/asrhub-backup
0 3 * * * asrhub sqlite3 /var/lib/asrhub/asrhub.db \
  ".backup '/резерв/asrhub-$(date +\%F).db'" && \
  find /резерв -name 'asrhub-*.db' -mtime +30 -delete
```

## Сводка по расписанию

Тревоги мониторинга срабатывают на происшествия, а на вопрос «как шли дела в целом» отвечает раздел аналитики — куда надо зайти. Отчёта, который никто не открывает, не существует, поэтому сводку можно получать самому.

| Настройка | По умолчанию | Что задаёт |
|---|---|---|
| `digest_interval_hours` | `0` (не отправлять) | как часто отправлять |
| `digest_url` | пусто | куда: входящий адрес чата, свой обработчик, шлюз почты |
| `digest_period` | `week` | за какой срок считать показатели |

```yaml
digest_interval_hours: 168
digest_url: https://chat.example.com/hooks/asrhub
digest_period: week
```

Уходит `POST` с телом JSON: те же разделы, что у `GET /api/analytics`, плюс поле `text` — та же сводка словами. Приёмник входящих сообщений в мессенджере показывает именно `text` и про остальные поля не знает, так что в чат приходит читаемая сводка, а не свёрнутый JSON:

```
ASR Hub, сводка за период «week»
Заданий: 338, готово 321, ошибок 12
Звука обработано: 95.4 ч, слов 789373
Скорость: RTF 0.146 (в 6.8 раза быстрее реального времени)
Средняя уверенность: 0.926
Ожидание в очереди: p50 14 с, p95 64.8 с
Чаще всего падало: dependency_missing ×6, audio_error ×3

О чём говорили (312 разобранных записей)
Отрицательных разговоров: 11.5 % (36 из 312)
С упоминанием суда, жалоб и огласки: 7
Обещаний без названного срока: 24 из 96
Скрипт разговора соблюдён на 71 %
С признаками раздражения клиента: 41 (13.1 %)
Повторных обращений по нерешённому вопросу: 27 (8.7 %)
  ! У Петрова доля отрицательных разговоров вдвое выше средней по всем
  ! Разговоры после 18:00 идут тяжелее дневных
  + Скрипт стал соблюдаться лучше, чем в прошлом периоде
```

Если у сервера есть подозрительные расшифровки за период или записи без метки согласия (настройка `consent_tag`), в первой части появляются строки «Подозрительных расшифровок: 30 из 211 (14.2 %)» и «Записей без метки согласия старше срока: 12».

Второй блок — из раздела «Аналитика записей»; он появляется, только если за период есть разобранные записи и разбор включён (`content_analysis`). Строки со значком `!` и `+` — готовые выводы, не более трёх: те же, что на вкладке «Свод», отобранные по силе расхождения. Порядок блоков не случаен: сводку читают сверху вниз, а «сервер жив и справляется» — условие, при котором вторая половина вообще что-то значит.

В теле JSON тот же материал лежит в поле `content`: `summary`, `findings` и состояние разбора. Если разбор выключен или за период не разобрано ни одной записи, поля просто нет — пустого блока в тексте не будет.

Сводка считается по всем заданиям, без разреза по владельцу: она уходит тому, кто отвечает за сервер целиком. В теле есть поле `instance` — имя машины и номер процесса: на общей базе серверов несколько, и без него первый же вопрос получателя остаётся без ответа.

Сбой отправки никогда не влияет на работу сервера: сводка — это удобство, а не часть обработки заданий. Неудача пишется в журнал, следующая попытка будет по расписанию.

## Очистка

Дисковое пространство расходуют три вещи: загруженные файлы, результаты и веса моделей.

```bash
curl -X POST http://127.0.0.1:8080/api/maintenance/cleanup -H "X-API-Key: ключ"
```

Удаляются задания, завершённые раньше чем `result_retention_days` назад (по умолчанию 30 дней), метрики старше 180 дней и события старше 90. Настройки хранения:

```yaml
result_retention_days: 30      # 0 — хранить вечно
delete_source_after: true      # удалять загруженный файл сразу после обработки
```

`delete_source_after: true` — правильное значение для большинства случаев: исходники обычно есть у отправителя, а на сервере они только занимают место. Оставьте `false`, только если сервер — единственное место, где записи хранятся.

Веса неиспользуемых моделей:

```bash
bash scripts/models.sh disk                     # сколько чем занято
bash scripts/models.sh remove whisper-large-v2  # удалить конкретную
```

## Управление памятью

```yaml
model_cache_size: 2            # сколько моделей держать загруженными
model_idle_unload_s: 900       # выгрузить после 15 минут простоя
gpu_memory_fraction: 0.9       # доля видеопамяти, доступная процессу
```

Загрузка модели занимает от 5 до 40 секунд. При потоке однородных заданий держать модель в памяти выгодно — иначе загрузка съест больше времени, чем распознавание. Показатель `model_load_share` в разделе «Эффективность» показывает, насколько это актуально именно у вас: если он выше 0,2, увеличьте кеш или время выгрузки.

При разнородном потоке и ограниченной памяти, наоборот, полезно уменьшить `model_cache_size` до 1: две большие модели одновременно могут не поместиться, и вы получите ошибки нехватки памяти вместо небольшой задержки.

## Несколько серверов над одной базой

Один сервер держит очередь, кеш и реестр движков в памяти процесса, и до недавнего времени два сервера над общей базой брали одно и то же задание: статус читался, потом записывался, и между этими двумя действиями оба успевали решить, что задание свободно. Платили дважды — за GPU и за уведомление, которое уходило дважды.

Теперь задание захватывается одним неделимым действием: `UPDATE ... WHERE status IN ('queued','retry')`. Кто успел первым — тот и считает; второй получает ноль изменённых строк и идёт за следующим. Отдельного координатора для этого не нужно: роль арбитра играет сама база.

Каждый экземпляр подписывает взятое задание своим именем (`имя_машины:pid`) и обновляет отметку жизни, пока считает. Кто чем занят — видно в состоянии очереди:

```bash
curl -s -H "X-API-Key: $КЛЮЧ" http://сервер:8080/api/queue | python3 -m json.tool
```

```json
{
  "instance": "asr-1:2417",
  "instances": [
    {"instance": "asr-1:2417", "self": true,  "jobs": 2, "last_seen_s": 1.2,   "stale": false},
    {"instance": "asr-2:1908", "self": false, "jobs": 1, "last_seen_s": 412.0, "stale": true}
  ]
}
```

`stale: true` означает, что экземпляр не обновлял отметку дольше пяти минут. Его задания будут возвращены в очередь и посчитаны заново — с записью `reclaimed` в журнале задания:

> Экземпляр «asr-2:1908» перестал отвечать — задание возвращено в очередь (попытка 1 из 3)

Без этого сервер, убитый по нехватке памяти или остановленный вместе с машиной, оставлял свои задания в состоянии «выполняется» навсегда: пользователь видел вечные 40 % и не мог ни дождаться, ни понять, что случилось. Свои задания экземпляр не подбирает никогда — его собственный поток может просто задержаться на загрузке весов. Перезапуск сервера тоже забирает только свои задания и ничьи: чужие остаются соседям, даже если выглядят зависшими.

**Возврат считается попыткой.** «Убит по нехватке памяти» обычно повторяется на одном и том же файле, и без счётчика задание возвращалось бы в очередь без конца, убивая экземпляры один за другим — молча, без отказа и без сигнала администратору. Когда попытки исчерпаны, задание снимается с ошибкой `instance_lost`:

> Экземпляр «asr-2:1908» перестал отвечать, попыток израсходовано: 3.

Это диагноз: дело в самом файле, а не в сервере. Смотрите память на машине — чаще всего так выглядит `out_of_memory`, который успевает убить процесс раньше, чем тот запишет ошибку.

**Ожившего мертвеца не пускают.** Экземпляр, застрявший дольше пяти минут (своп, ввод-вывод, долгая загрузка весов) и вернувшийся к жизни, не может дописать свой ответ в задание, которое уже считает другой сервер: при записи результата сверяется не только статус, но и имя экземпляра. Иначе пользователь получал бы ответ от процесса, объявленного мёртвым, а работа второго экземпляра выбрасывалась вместе с каталогом выгрузки.

**Что нужно для такой раскладки**

| Что | Как |
|---|---|
| Общий каталог данных | `data_dir` (переменная `ASRHUB_DATA_DIR`) на общем хранилище. От него производны и база, и загрузки, и результаты — разносить их по отдельности нельзя |
| Видимость файла с обеих сторон | задание может взять другой сервер, и загруженный файл должен быть виден ему по тому же пути. Отсюда и требование одного каталога, а не только общей базы |
| Балансировщик | любой; сессий нет, липкость не нужна |
| Ключи доступа | один и тот же `config.yaml` на всех: ключ, созданный на одном сервере, о другом не знает |

⚠️ SQLite по сети — не лучшая мысль: журнал WAL требует настоящих блокировок, а NFS их обещает не всегда. Для двух-трёх серверов рядом на одном хранилище это работает; для большего — задача другого класса, и честный ответ здесь «этого в проекте нет».

**Обслуживание такой раскладки.** Скрипты знают о соседях и не действуют вслепую:

| Команда | Что делает с общим каталогом |
|---|---|
| `install.sh --data /общий/путь` | Не отбирает каталог: если он принадлежит другому пользователю, спрашивает, а не делает молчаливый `chown -R`, после которого соседи теряют доступ к своей же базе |
| `install.sh --name asrhub-2` | Задаёт имя службы. Без него вторая установка на машине перезаписала бы юнит первой |
| `uninstall.sh` | Останавливает процессы только своей установки — по каталогу программы, а не по слову «asrhub» в командной строке |
| `uninstall.sh --purge` | Сначала спрашивает базу, работает ли над ней кто-то ещё, и предупреждает, что удалит и их данные |
| `update.sh` | То же: предупреждает, что после обновления версии на машинах разойдутся, и предлагает остановиться |

Обновлять экземпляры лучше подряд и без большого разрыва: схема базы совместима, но разные версии сервера над одной базой — самый неприятный вид расхождения, он воспроизводится через раз.

Отметка жизни настраивается на стороне кода (`STALE_AFTER_S`, пять минут). Значение стоит держать заметно больше самой долгой загрузки весов: иначе задание отберут у живого сервера, который просто грузит модель.

## Обновление моделей и кеш результатов

Кеш отвечает готовой расшифровкой, когда совпали содержимое файла и настройки задания. Имя модели при этом ничего не говорит о том, какие веса за ним стоят: GigaAM и Whisper выкладывают новые ревизии под тем же идентификатором, и старый результат уходил пользователю как свежий — без единого признака, что он посчитан прошлой версией.

Теперь в ключ кеша входит отпечаток файлов модели: пути, размеры и время изменения. Обновили веса — отпечаток изменился, кеш промахнулся, задание посчиталось заново. Ничего делать руками не нужно; `POST /api/maintenance/cleanup` после обновления модели больше не обязателен.

Отпечаток берётся по метаданным, а не по содержимому: веса весят гигабайты, читать их на каждое задание нельзя. Результат помнится минуту, чтобы не обходить диск на каждое задание, и сбрасывается сразу после загрузки или удаления модели через API. Если веса подменили руками, мимо `POST /api/models/{id}/download`, — в течение минуты кеш ещё может ответить по-старому.

Весов на диске нет (движок держит их в своём кеше) — отпечаток пуст, и кеш работает как раньше, по имени модели: хуже, чем с отпечатком, но не хуже, чем было.

## Мониторинг

Минимальный набор проверок:

```bash
curl -sf http://127.0.0.1:8080/api/health || echo "сервер не отвечает"
```

Что стоит выводить на график:

| Метрика | Тревожный признак |
|---|---|
| `asrhub_jobs_total{status="queued"}` | устойчивый рост — не хватает мощности |
| `asrhub_disk_free_gb` | приближение к `disk_min_free_gb` |
| `asrhub_rtf_p95` | рост при неизменной нагрузке — деградация железа или троттлинг |
| `asrhub_success_rate` | падение — смотрите раздел «Ошибки» |
| `asrhub_gpu_percent` | устойчивые 100 % — узкое место найдено |

Экспортер Prometheus включён по умолчанию (`metrics_enabled: true`), точка `/api/metrics` доступна без ключа: её закрывают на уровне прокси, если сервер смотрит в интернет.

Полноценный мониторинг — отдельный раздел [16. Мониторинг](16-monitoring.md): 63 метрики в семи форматах, пробы состояния, тревоги по порогам и готовые настройки для Prometheus, Grafana и Zabbix.

## Журналы

```bash
bash scripts/service.sh logs -n 500 -f
curl -H "X-API-Key: ключ" \
  "http://127.0.0.1:8080/api/logs?level=error&limit=100"
```

Файл журнала лежит в `<данные>/logs/asrhub.log` с ротацией. Уровень задаётся `log_level`; `DEBUG` включают на время разбора конкретной проблемы — он многословен.

Недоступный приёмник метрик жалуется в журнал один раз, а дальше — не чаще раза в час, и отдельной строкой сообщает, когда отправка восстановилась. Раньше это была строка в минуту круглосуточно: за ночь полторы тысячи одинаковых предупреждений, в которых тонет всё остальное. Полное состояние приёмников (сколько отправлено, сколько неудач, последняя ошибка) всегда видно в разделе наблюдения и по `GET /api/monitoring/push`.

⚠️ Параметр `log_transcript_text` по умолчанию **выключен**, и менять это не стоит. Включённый, он пишет распознанный текст в журнал — то есть содержание разговоров попадает в файл, который читают администраторы, забирает система сбора логов и хранит резервная копия. Для отладки достаточно карточки задания.

## Безопасность

Практический минимум:

1. **Аутентификация включена** (`auth_enabled: true`), ключи выданы поимённо. Ключ на каждую интеграцию — отозвать один, не трогая остальных.
2. **Роли по назначению.** Интеграции, которая только забирает результаты, нужен `readonly`.
3. **Сервер не смотрит в интернет напрямую.** HTTPS через прокси, VPN или SSH-туннель.
4. **Слушать localhost**, если доступ идёт через прокси на той же машине: `server_host: 127.0.0.1`.
5. **CORS закрыт** (`cors_origins: ""`), если браузерный доступ с других доменов не нужен.
6. **Отдельный системный пользователь** для службы, каталог данных с правами 0750.
7. **`delete_source_after: true`**, чтобы записи не накапливались.

Записи разговоров — чувствительные данные. Сервер распознавания хранит и загруженные файлы, и расшифровки; относитесь к нему как к хранилищу персональных данных, а не как к вычислительному узлу.

## Обновление

```bash
bash scripts/update.sh --check      # что изменится
bash scripts/update.sh              # обновить со снимком
bash scripts/update.sh --rollback   # вернуть предыдущую версию
```

Порядок для рабочего сервера:

1. Резервная копия базы (`.backup`).
2. `--check` — посмотреть, что меняется.
3. Пауза очереди, дождаться завершения текущих заданий.
4. Обновление.
5. `bash scripts/doctor.sh` и пробное задание.
6. Снять паузу.

Если после обновления что-то не так — `--rollback` возвращает код, конфигурацию и базу к состоянию до обновления.

Последним шагом обновление ждёт, пока сервер начнёт отвечать, и различает три исхода:

| Что видно | Что это значит |
|---|---|
| «Сервер отвечает — обновление успешно» | сервер поднялся на новом коде |
| «Сервер отвечает, но сообщает о неисправности» | код обновился и работает, сломано что-то под ним — чаще всего база или диск. Откат этого не лечит, смотрите тело ответа и `doctor.sh` |
| «Сервер не отвечает после обновления» | дальше печатается разбор: состояние службы, хвост её журнала, кто занял порт и пробный запуск пакета. Предлагается откат |

Порт для проверки спрашивается у самой службы (строка запуска юнита, а не только `config.yaml`): эти два места расходятся молча, и раньше работающий сервер на другом порту объявлялся мёртвым. Ожидание прерывается сразу, как только становится ясно, что служба упала, — минуту вхолостую скрипт не тратит. Если до обновления служба не работала, сервер не запускается и не проверяется: обновление на этом успешно заканчивается.

## Настройка производительности

Пошагово, от самого действенного:

1. **Проверьте, что задействован ускоритель.** `GET /api/system` покажет устройство. Задание, случайно посчитанное на процессоре, идёт в 10–30 раз дольше. Это самая частая причина «медленно».
2. **Включите VAD.** Тишина, паузы и музыкальные заставки составляют в записях совещаний до трети длительности. Не подавать их в модель — бесплатное ускорение без потери качества.
3. **Подберите `batch_size`.** Увеличивайте, пока не упрётесь в память. На видеокарте 12 ГБ с large-моделью обычно 8–16.
4. **Возьмите модель полегче там, где она достаточна.** `gigaam-v3-ctc` быстрее `gigaam-v3-rnnt` в полтора-два раза, а разница в WER — меньше процентного пункта.
5. **Уменьшите `beam_size`.** С 5 до 1 — примерно вдвое быстрее; качество проседает заметно только на сложном звуке.
6. **Проверьте `compute_type`.** На видеокарте `float16` вместо `float32` — вдвое быстрее и вдвое меньше памяти при неразличимом качестве. На процессоре — `int8`.
7. **Держите модель в памяти** между заданиями, если поток однородный.

Подробные сценарии с цифрами — [12. Сценарии настройки](12-tuning.md).

## Ежедневные проверки

```bash
#!/usr/bin/env bash
# Утренняя сводка: живость, очередь, ошибки за сутки, место на диске.
СЕРВЕР=http://127.0.0.1:8080
КЛЮЧ=ah_ваш_ключ

curl -sf "${СЕРВЕР}/api/health" >/dev/null || { echo "СЕРВЕР НЕ ОТВЕЧАЕТ"; exit 1; }

curl -s -H "X-API-Key: ${КЛЮЧ}" "${СЕРВЕР}/api/queue" \
  | jq '{ожидают: .queued, выполняются: .running, воркеров: .workers}'

curl -s -H "X-API-Key: ${КЛЮЧ}" "${СЕРВЕР}/api/analytics/errors?period=day" \
  | jq '.by_code'

df -h /var/lib/asrhub | tail -1
```
