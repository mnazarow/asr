# Ревизия кода: что исправлено и что осталось

Раздел составлен по итогам полной проверки кода — сервера, подсистемы
мониторинга, скриптов установки и веб-интерфейса. Находки проверялись
запуском, а не чтением: гистограммы измерялись, аутентификация проверялась
запросами, скрипты прогонялись на макетах каталогов.

Здесь два списка: что уже исправлено и что осталось. Второй важнее — он
показывает, где система слабее, чем кажется по документации.

## Исправлено

### Установка и обслуживание

| Что было | Чем грозило |
|---|---|
| `install.sh` падал, когда все системные зависимости уже установлены: пустой массив + `grep` без совпадений + `pipefail` | Установка не проходила именно на укомплектованной машине. Самый разрушительный дефект: первое впечатление от продукта — откат и сообщение об ошибке |
| `uninstall.sh` без `--purge` сносил каталог данных на macOS | Потеря моделей, базы и результатов — при том что скрипт тут же писал «Данные сохранены». Каталог данных там лежит **внутри** каталога программы |
| `update.sh --rollback` вызывал `rsync --delete` поверх снимка, где лежит только код | Откат обновления уничтожал виртуальное окружение, а на macOS — и данные |
| `pkill -f "asrhub"` при удалении | Под удаление попадал любой процесс, у которого «asrhub» встречается в командной строке: редактор, `tail -f`, соседний шелл |
| Мастер установки перетирал `--profile`, `--engines`, `--models` | Ключи командной строки молча игнорировались |
| `xargs -r` и `grep -E '^\s*'` — расширения GNU | На macOS обновление обрывалось после резервной копии базы, а порт для проверки здоровья определялся неверно |
| `[[ "${WAS_RUNNING}" -eq 1 \|\| true ]]` — условие истинно всегда | Служба поднималась после обновления даже если её остановили намеренно |

### Безопасность

| Что было | Чем грозило |
|---|---|
| WebSocket `/ws` не проверял ключ вообще | Полный обход аутентификации: любой, кто дотянулся до порта, видел имена файлов, статусы и ошибки всех заданий в реальном времени |
| `DELETE /api/keys/{preview}` сопоставлял по `key.startswith(preview[:6])` | Все ключи начинаются с `ah_`, поэтому `DELETE /api/keys/a` отзывал первый попавшийся — в том числе действующий ключ администратора |
| Роль `user` не проверялась на владельца задания | Любой ключ с правом записи мог отменить, переставить и удалить чужое задание вместе с результатами |
| `POST /api/jobs/batch` не соблюдал `max_upload_mb` и не ограничивал число файлов | Ключ с ролью `user` забивал диск пакетом любого размера |
| Адрес webhook не проверялся и уходил в `urlopen` | Сервер обращался во внутреннюю сеть от своего имени: `file://` читал диск, `169.254.169.254` доставал учётные данные облака |
| Имя модели попадало в формат Prometheus без экранирования | В выгрузку метрик можно было вписать поддельные значения |
| Файл с автоматическим ключом создавался, а права выставлялись после | Окно, в котором ключ доступен на чтение всем |

### Потеря данных и работоспособности

| Что было | Чем грозило |
|---|---|
| `Settings.save()` не сохраняла ключи доступа, а файл переписывался целиком | Один вызов «Сохранить настройки» — и все ключи потеряны при следующем перезапуске. Ключи, созданные через API, вообще нигде не сохранялись |
| Миграции не умели добавлять колонки: `CREATE TABLE IF NOT EXISTS` не трогает существующую таблицу | После обновления база прошлой версии давала «no such column» на каждом запросе |
| Модель выгружалась из памяти посреди распознавания | `last_used` обновлялось только на границах, а простой в 900 секунд короче обычного совещания. То же при вытеснении из кеша |
| Один экземпляр движка работал из нескольких воркеров без блокировки | Модели PyTorch и CTranslate2 не рассчитаны на одновременный вызов |
| `cleanup()` удалял записи, но не файлы | Диск рос монотонно, хотя подсказка к ошибке «нет места» отправляет пользователя именно в эту очистку |

| Аналитика выбирала до 100 000 полных строк вместе с колонкой `text` | Страница аналитики на большой базе съедала гигабайты и клала сервер |

### Второй заход: конвейер и планировщик

| Что было | Чем грозило |
|---|---|
| Отмена проверялась только на границах этапов | Кнопка «Отменить» не действовала всё время распознавания — на часовой записи это десятки минут. Признак отмены теперь проверяется в обработчике прогресса, то есть внутри движка, на ближайшей границе фрагмента |
| `cancel()` читал задание вне блокировки и писал без условия на статус | Успешное задание получало статус «отменено» и наоборот. Заменено на `UPDATE … WHERE status = ?` |
| Уведомление создавало поток на каждое задание | Пакет из тысячи заданий с недоступным получателем — тысяча потоков по четыре минуты каждый. Введён ограниченный пул |
| Планировщик отбирал кандидатов по приоритету и лишь потом применял политику | Политики `deadline` и `fair_share` работали на верхушке очереди: срочное задание с низким приоритетом не выбиралось никогда |
| `_find_cached` сравнивал хеши среди 50 последних заданий в Python | При потоке больше 50 заданий дедупликация не работала вовсе, хотя индексированный `find_cached()` в базе уже был написан |
| Клон из кеша делил каталог результатов с оригиналом | Удаление любого из двух заданий уничтожало результаты второго |
| `set_concurrency` при уменьшении не убирал лишние потоки | Последовательность 2 → 8 → 2 оставляла восемь живых потоков, и `status()` показывал их как рабочие |
| `recover()` разбирал не больше тысячи заданий | После аварии лишние зависали в «выполняется» навсегда |
| `RTF` складывал все стадии, включая загрузку модели | Показатель завышался в разы относительно того, что публикуют авторы моделей |
| `_mini_yaml` терял списки верхнего уровня | Без PyYAML списки в файле конфигурации молча отбрасывались |
| Служебный цикл очереди целиком под `except Exception` с уровнем `debug` | Постоянно падающая очистка диска не давала ни одной записи при штатном уровне INFO |
| Надстройки постобработки молчали при недоступности | Пользователь просил расстановку знаков препинания, получал текст без них и нигде не видел почему. Явно выбранная надстройка теперь сообщает о себе предупреждением |

### Третий заход: разграничение доступа

Проверка стояла на одном пути и отсутствовала на соседнем — самый частый вид
дефекта в этом заходе.

| Что было | Чем грозило |
|---|---|
| `GET /api/jobs` не фильтровал по владельцу | Карточка задания давно закрыта `require_owner`, а список — нет. Любой выданный ключ получал одним запросом чужие задания: имя файла, путь на диске, полную расшифровку. Проверено запросом: Боб видит задание Алисы в списке и получает 403 на ту же карточку |
| То же в аналитике | Разделы «ошибки» и «самые медленные» показывали чужие имена файлов, «по владельцам» — весь список тех, кто пользуется сервером |
| `GET /api/logs` был доступен любому ключу | Журнал несёт имена чужих файлов, тексты ошибок и трассировки. Теперь требует администратора: разделить журнал по владельцам нечем — строка пишется до того, как известен ключ |
| Лента событий отдавалась целиком | События ссылаются на задания и несут имена файлов |
| Запрет на внутреннюю сеть обходился строкой в JSON | Поле формы `webhook_url` проверялось, а то же значение внутри `settings` — нет. `settings={"webhook_url":"http://169.254.169.254/..."}` проходил, сервер сам шёл по адресу, а поле `webhook_status` работало оракулом для обхода внутренней сети. `file:///etc/passwd` тоже проходил |
| `/api/metrics` не проверял ничего | Администратор закрывал метрики настройкой `monitoring_public: false`, `/api/monitoring/metrics` честно отвечал 401 — а этот адрес отдавал тот же снимок из 109 метрик кому угодно. Хуже стало после того, как оба адреса свели к одному экспорту: утечка выросла с пятнадцати метрик до всех |
| `webhook_secret` уходил в `GET /api/settings` | Ключ «только чтение» получал секрет подписи уведомлений открытым текстом — то есть возможность подделывать результаты для принимающей стороны |

| Отклонённая загрузка оставляла файл на диске | Файл писался до разбора полей формы, а разбор стоял вне защиты: каждая опечатка в имени параметра оставляла копию записи в `uploads`, на которую не ссылается ни одно задание — уборщик её не найдёт никогда. Пять отклонённых запросов — пять осиротевших файлов |
| В каждый выгруженный файл уходили нули | `to_result` читает замеры, а проставлялись они после записи файлов: в `result.json` и в отчёте DOCX стояли «rtf: 0.0» и «время обработки: 0», тогда как в интерфейсе по тому же заданию — настоящие значения. Выглядело как порча данных при выгрузке |
| Разбор ошибок в аналитике был пуст | Облегчённый список не нёс `error_message`, `error_hint` и `filename`: экран, ради которого его и открывают, показывал коды со счётчиками и пустые столбцы «сообщение» и «что делать» у всех строк |
| Политика планирования по сроку не работала | `deadline` не входил в облегчённый набор колонок, поэтому срок всегда читался как «не задан» и планировщик молча уходил в обычный `priority_fifo`. Настройка при этом честно возвращалась в статусе очереди |
| Уведомление не уходило при попадании в кеш | Повторная подача того же файла завершалась мгновенно из кеша — и колбэк не приходил никогда, а адрес не переносился в клон, так что и повторить отправку было нечем. Внешняя система висела до собственного тайм-аута |
| Легальный ноль подменялся значением по умолчанию | `float(settings.get(key) or ЗАПАСНОЕ)` срабатывает на нуле, а ноль у двенадцати параметров — осмысленная величина на краю диапазона: `no_speech_threshold: 0` отключает отбраковку тишины, `job_timeout_s: 0` снимает ограничение времени. Пользователь ставил ноль, интерфейс принимал, задание пересчитывалось — и возвращался прежний результат. По журналу не диагностируется |
| Детектор речи объявлял речью почти тихую запись | Пик брался как 95-я перцентиль энергии; если речи меньше пяти процентов, в перцентиль попадал шум, порог вставал ниже шумовой полки, и час тишины уходил в движок целиком. Проверено на записи с двумя секундами речи из шестидесяти: детектор находил 60 из 60 секунд, стало 2,4 |

### Четвёртый заход: сценарии установки

Область, до которой прошлые проходы не доходили. Эти сценарии выполняются на
чужой машине, часто от root, поэтому цена ошибки здесь выше, чем в сервере.

| Что было | Чем грозило |
|---|---|
| `update.sh`, запущенный из самой установки, удалял каталог `server` | Это ровно та команда, которую установщик печатает в разделе «Что дальше»: `bash <PREFIX>/scripts/update.sh`. Источник и назначение совпадают, цикл сначала делал `rm -rf`, потом `cp -a` из уже удалённого каталога. Установка оставалась разобранной, а сообщение об ошибке не говорило про снимок и `--rollback`. Проверено прогоном |
| `confirm()` отвечал «да» без терминала | `ssh машина 'bash uninstall.sh'`, задача Ansible, строка в cron — полное удаление без единого вопроса, притом что вопрос задан с умолчанием «нет». Проверено: каталог программы снесён, код возврата 0 |
| `--dry-run` создавал и включал службу systemd | Флаг не экспортировался, а `service.sh` запускается отдельным `bash` — в дочернем процессе он снова становился нулём. «Пробный запуск» оставлял на машине включённый в автозапуск юнит, указывающий в никуда, а пробное удаление гасило работающую службу |
| `--purge --keep-models` удалял модели, которые обещал сохранить | Перенос стоял после `rm -rf "${PREFIX}"`, а на macOS каталог данных лежит внутри prefix. К моменту переноса каталога уже не было, и скрипт дважды отчитывался об успехе при пустом диске |
| `uninstall.ps1` на Windows удалял данные и писал «Данные сохранены» | При установке без прав администратора каталог данных лежит в `%LOCALAPPDATA%\ASRHub\data`, то есть внутри программы. В bash-версии защита была, в PowerShell — нет |
| `readarray` на основном пути установки | Появился в bash 4.0, а macOS штатно поставляет 3.2.57. Ветка срабатывает всегда, когда чего-то не хватает, — а на свежем Mac всегда не хватает ffmpeg. Установка обрывалась на втором шаге, и подсказка звала «установить недостающую программу», хотя не хватало встроенной команды оболочки |
| Установка в контейнере всегда завершалась кодом 1 | `FAILED_ENGINES` заполняется только в нативном режиме, а читается в конце для обоих; под `set -o nounset` это роняло скрипт уже после слов «Установка завершена». Ansible, CI и Makefile считали успешную установку провалом |
| Мастер перетирал `--host` и `--no-service` | `--host 127.0.0.1` — это «не выставлять наружу»; сервер оказывался доступен всей сети, а служба автозапуска создавалась вопреки ключу |

### Пятый заход: разграничение доступа

Прошлый заход закрыл `GET /api/jobs` через сужение по владельцу. Оказалось,
что это была одна дверь из семи.

| Что было | Чем грозило |
|---|---|
| `GET /api/queue` отдавал задания всех владельцев | Выборка шла без `owner` и без `light`. Любой ключ, включая `readonly`, получал имена чужих файлов, пути на диске, готовые расшифровки и адреса уведомлений вместе с токенами внутри. Тот же ответ рисуется на главном экране |

Пустым `result_path` становится штатно — когда каталог-источник исчез между проверкой кеша и копированием |
| Задание с пустым владельцем читал и удалял кто угодно | Проверка выглядела как `if owner and owner != …`, то есть пустое значение означало «проверять нечего». Такие записи создаёт клиент командной строки и ключ без имени |

| `GET /api/system` отдавал раскладку файловой системы любому ключу | Сама по себе разведка, но именно она превращает две находки выше из теоретических в применимые |
| Предел размера загрузки проверялся после приёма тела | Это стояло в списке «осталось» с прошлого захода. Теперь предел проверяется по `Content-Length` в middleware, до маршрутизации: при `max_upload_mb=1` до разбора multipart не доходит ни одного байта, тогда как раньше во временный файл успевало осесть 40 МБ |

### Седьмой заход: ревизия того, что сделал шестой

Заход проверял не старый код, а свежий — тот, которым закрывали ограничения.
Находки этого рода самые неприятные: возможность объявлена работающей, и
никто больше на неё не смотрит.

**Сервер**

| Что было | Чем грозило |
|---|---|
| Кадр от десяти секунд намертво вешал поток | В ffmpeg писали весь кадр разом, а вывод забирали только после записи. Труба вывода вмещает 64 КБ: ffmpeg упирался в неё, переставал читать вход — а мы уже ждали на записи. Обе стороны замирали навсегда, при том что документация обещает «размер любой». Заодно и профиль подбирался как для машины без карты — за минуту до того, как установщик сам поставит драйвер |
| Проверка venv смотрела не на то | `import venv` проходит всегда — это стандартная библиотека. В Debian и Ubuntu отдельным пакетом идёт `ensurepip`, без которого `python -m venv` доходит до конца и падает. Установка сваливалась в откат на шестом шаге вместо того, чтобы поставить один пакет на втором |
| Имя пакета venv не учитывало интерпретатор | Метапакет `python3-venv` тянет `ensurepip` для того Python, который в системе основной. На сервере с `python3.14` из стороннего репозитория установка падала второй раз тем же способом |
| Ловушка `ERR` не наследовалась функциями | Не был включён `errtrace`, а вся работа скриптов происходит в функциях. Сбой в мастере, в загрузке, в установке пакетов или в настройке видеокарты завершал установку с кодом 1 — без сообщения, без журнала и без отката, который шапка `install.sh` обещает прямым текстом |
| Проверка порта врала под `pipefail` | `grep -q` рвал трубу, `ss` получал SIGPIPE, код конвейера становился 141 — «не нашли». На любой машине, где сокетов больше, чем влезает в буфер трубы, занятый порт объявлялся свободным: доктор сообщал «сервер не запущен», а установщик вёл установку на занятый порт. Тот же дефект прятал службу на macOS (и обновление не поднимало сервер обратно) и рабочую видеокарту Intel |
| Обновление обрывалось без `config.yaml` | `grep` возвращает 2, когда файла нет; `pipefail` с `errexit` превращали это в выход на последнем шаге — при том что код и зависимости уже заменены. Установка без файла конфигурации — случай штатный и самый частый |
| Каталог данных получал 0755 вместо 0750 | `check_disk_space` создавал его первым обычным `mkdir`, и `ensure_dir` видел каталог существующим — `chmod` пропускался. В этом каталоге лежит `config.yaml`, куда сервер дописывает ключи доступа с их подразделениями и квотами; сам файл создавался по umask, то есть 0644 |
| `--dry-run` создавал каталоги | И тут же писал «изменений не вносилось» |
| Удаление убивало чужие экземпляры | `pgrep -f "python.*asrhub"` ловил соседнюю установку в другом каталоге и на другом порту, а заодно любую постороннюю оболочку, у которой эти слова оказались в командной строке |
| `chown -R` отбирал общий каталог данных | `useradd --system` даёт на каждой машине свой uid, поэтому вторая установка делала базу нечитаемой для первой |
| Юнит systemd ломался на пробелах в путях | `ExecStart` искал программу «/opt/asr», `ReadWritePaths` отбрасывался целиком — а вместе с `ProtectSystem=full` это делает каталог данных доступным только на чтение. Там же `StartLimit*` стоял в секции `[Service]`, где systemd его игнорирует: задуманные «5 попыток за 120 с» не работали |
| Половина движков никогда не обновлялась | Имя файла требований превращали в имя модуля через `tr '-' '_'`, а у `diarization`, `vad`, `postprocess`, `mfa`, `qwen3-asr` и ещё нескольких такого модуля нет вовсе. Проверка молча не срабатывала |
| Нативная установка принималась за докерную | `docker-compose.yml` лежит в любой копии исходников. Зависимости не обновлялись, а дальше шла пересборка образа на машине, где docker никогда не использовали |
| `models.sh disk` обрывался на полуслове | `head` закрывал трубу, `sort` умирал от SIGPIPE: на кеше из тысяч каталогов отчёт кончался, не дойдя ни до итога, ни до свободного места |
| В отчёте доктора вместо подразделений стоял ноль | Переменная называлась `GROUPS` — это служебное имя bash с массивом групп пользователя, и запись в неё через `read` не проходит |
| Мастер PowerShell затирал ключи командной строки | `-Profile`, `-BindHost`, `-Engines` молча пропадали: умолчания мастера были записаны в коде числами. `-BindHost 127.0.0.1` превращался в `0.0.0.0` — сервер выставлялся в сеть вопреки прямому указанию |
| Раздел движков в `doctor.ps1` падал всегда | В here-string обратная косая ничего не экранирует, и `\"` уходило в Python дословно. Ошибка внешней программы не является ошибкой PowerShell, поэтому `catch` её не ловил: пользователь видел трассировку Python, а раздел не попадал ни в «пройдено», ни в «ошибок» |
| `update.ps1` не умел обновлять установку в контейнере | Образ не пересобирался, работающий контейнер отвечал на проверку живости старым кодом — и обновление объявлялось успешным, ничего не изменив |
| `Confirm-Action` роняла скрипт без консоли | Признаком интерактивности был `UserInteractive`, истинный и при перенаправленном вводе. В задаче планировщика, WinRM или CI дело доходило до `Read-Host`, а тот бросает исключение — и удаление или обновление обрывалось аварийно |
| `du -sb` на macOS всегда показывал «0 Б» | Ключ `-b` — расширение GNU |
| `asrctl models --installed` печатал весь каталог | Ключ разбирался и не использовался нигде. Теперь он есть и на сервере: `GET /api/models?installed=true` |

**Чего скрипты не знали о сервере**

`doctor.sh` не проверял ни поток, ни квоты, ни число экземпляров — всё это либо работает, либо тихо не работает, и заметить второе было нечем. Мастер установки не спрашивал про распознавание на лету и не предупреждал, что микрофон в браузере требует https. `examples/` не копировался в установку вовсе — при том что раздел «Диктовка» дважды отсылает к `examples/stream_microphone.py` как к пути без микрофона. Ни один скрипт не знал про раскладку с общим каталогом данных: имя службы не передавалось, и вторая установка перезаписывала юнит первой.

Всё перечисленное закрыто и покрыто регрессиями — они в `tests/test_install_scripts.py` и гоняют настоящий bash и `systemd-analyze` на макетах каталогов.

**Токен Hugging Face: вопрос в мастере и четыре дефекта по дороге**

Токен спрашивался только ключом `--hf-token`, то есть теми, кто уже знал про
него. Мастер теперь задаёт вопрос сам — отдельным шагом, с текстом,
зависящим от того, выбрано ли разделение по говорящим. Пока это делалось,
нашлось четыре отдельных дефекта; каждый воспроизведён запуском.

| Что было | Чем грозило |
|---|---|
| Токен доходил только до `docker/.env` | При обычной установке — а это подавляющее большинство — введённое значение молча пропадало. Человек отвечал на вопрос, а диаризация всё равно падала на седьмом шаге с «нужен токен». Переменные окружения читает systemd, но не launchd на macOS, не служба Windows и не запуск руками; `config.yaml` читают все четыре — теперь токен пишется туда |
| Первое сохранение настроек стирало токен | `hf_token` не относится ни к одной группе каталога, и `save()` его не писал. Сервер сохраняет настройки сам при первом запуске — когда выпускает ключ доступа, — то есть терял записанный установщиком токен раньше, чем тот успевал понадобиться |
| Первое сохранение настроек раздавало права на файл | Запись шла через временный файл, а `replace()` отдаёт цели права **временного** — то есть 0644 по umask. Установщик ставил на `config.yaml` 0640, и первый же запуск сервера делал файл с ключами доступа и токеном читаемым для всех в системе |
| Сводка мастера падала на русских подписях | `${#переменная}` в локали `C` считает байты: «Распознавание на лету» — 20 символов и 40 байт. Хуже того, функция заканчивалась на `(( ))`, а ложное условие — это код возврата 1: под `errexit` установка обрывалась прямо на сводке, с сообщением «Сбой на шаге: неизвестный шаг», по которому причину не найти. Ровно этот же приём (`(( )) && …`) убран и в обходе областей памяти видеокарты, где он пока сходил с рук |

Заодно: пункт «Разделение по говорящим» в мастере появился только сейчас —
без него условие «выбрана диаризация» не сработало бы никогда; проверка
токена (`hf_` и не меньше шестнадцати знаков) теперь одна и та же в bash и в
PowerShell и сверяется тестом построчно; в сводке видны первые шесть знаков и
длина, целиком токен на экран не выводится; в `config.example.yaml`, который
читается всеми, его нет и не появляется.

**GigaAM и обработка ошибок установщика**

Восьмой заход начался с письма, где на девяти экранах вывода pip повторялось
одно и то же: `gigaam 0.2.0 depends on onnxruntime==1.23.*`. Разбор этого
случая закончился двумя вещами — движок теперь ставится, а установщик умеет
называть причину отказа вместо того, чтобы отдавать пользователю стену
чужого вывода.

| Что было | Чем грозило |
|---|---|
| GigaAM не ставился совсем | В его `pyproject` версии прибиты гвоздями: `onnxruntime==1.23.*` и `onnx==1.19.*`, а колёс под Python 3.14 у них нет. pip обрывался с `ResolutionImpossible` ещё до загрузки пакета — при том что для распознавания ни `onnx`, ни конкретная версия `onnxruntime` не нужны, они только для экспорта в ONNX. Теперь пакет ставится с `--no-deps`, а зависимости перечислены своими руками |
| Движок из репозитория считался неустановленным | Имя пакета вырезалось по `<>=!;[`, а прямая ссылка PEP 508 выглядит как «gigaam @ git+https://…»: именем становилась вся строка с адресом. `update.sh` такой движок не видел и не обновлял никогда |
| Отказ pip не объяснялся ничем | Сто строк вывода и «установка не удалась — сервер запустится без него». Причину пользователь искал сам. Теперь вывод разбирается: прибитая версия, конфликт, отсутствующее колесо, DNS, прокси, сертификат, обрыв связи, место на диске, нехватка памяти, отсутствие компилятора, PEP 668, испорченный кеш — двенадцать причин, каждая с командой, которая её лечит |
| В автономном режиме диагноз был неверным | Без индекса pip говорит те же слова «No matching distribution found», и совет про версию Python уводил в сторону от настоящей причины — пустого кеша |
| Две установки в один каталог работали молча | Второй установщик сносит venv, пока первый в него ставит пакеты. На выходе установка, где половина движков есть, а половины нет, причём в журнале обеих всё успешно. Теперь стоит замок, который снимается сам — в том числе после Ctrl+C и после прерванной установки |
| Отсутствие git выяснялось на девятом шаге | Движки из репозитория pip клонирует сам; без git установка обрывалась после того, как окружение собрано и torch выкачан |
| Раздел с `noexec` обнаруживался ошибкой pip | Виртуальное окружение на таком разделе собирается успешно и не работает: «Permission denied» на собственный python. По этому сообщению причину не найти |
| Нет прав на запись — выяснялось в середине копирования | Проверка стоит доли секунды и делается теперь до всего |
| После сбоя приходилось вспоминать ключи | Последней строкой печатается команда, которой установка повторяется. Токен Hugging Face в ней замаскирован: строка попадает и в журнал |
| «Команда: return ${status}» в отчёте о сбое | Внутренняя строка библиотеки на месте, где ожидается причина. Настоящая причина названа выше разбором вывода — эта строка только мешала |
| `models.sh` обещал журнал, которого не вёл | «Полный вывод: журнал не велся» — ровно в том месте, где подробности нужнее всего. Журнал теперь заводят все скрипты, а полный вывод pip при отказе дописывается в него. Журнал дочернего процесса не подменяется: `install.sh` запускает `models.sh` и `service.sh` отдельными bash, и записи всех троих ложатся в один файл |
| У `models.sh` не было ловушки ошибок | Сбой внутри функции завершал скрипт кодом 1 молча. Доктору и управлению службой ловушку, наоборот, не ставили: у них ненулевой код — штатный ответ («проверка не пройдена», «служба остановлена»), и обрывать на нём работу значило бы превращать обычный ответ в аварию |
| `remove-engine` оставлял сам движок | Список к удалению собирался только по обычному файлу требований, а пакет из репозитория перечислен в спутнике. Заодно `grep -v` возвращает единицу, когда отбросил все строки: на файле из одних комментариев скрипт умирал бы под errexit, ничего не удалив |
| Подкаталог `no-deps` предлагался как движок | Список доступных движков собирался обходом всего каталога с обрезанием «.txt» |
| protobuf переставлялся дважды за обновление | NeMo объявляет `protobuf~=5.29.5` и утаскивал окружение вниз, а `transformers` следом возвращал его наверх. Дело не в лишней работе: на 5.29 `googleapis-common-protos` (внутри `pyannote.audio`) падает при импорте с `VersionError`, потому что его код сгенерирован версией 6.33.5, — то есть каждое обновление проводило окружение через состояние, где диаризация сломана, и спасало только то, что `transformers` стоит в очереди после `nemo`. Версию теперь задаём мы сами, файлом `requirements/overrides.txt`, и применяется он после всех движков |
| Служба работала по устаревшему определению | systemd в каждой команде предупреждал «unit file … changed on disk», и предупреждение было буквальным: правки юнита лежали на диске, но в работе не участвовали. Перезагрузку делала только установка, а `update.sh` юнит не переустанавливает. Добавленные каталоги кеша так и не действовали, и жалобы в журнале копились снова. Теперь `service.sh` перед каждой командой спрашивает `NeedDaemonReload` и перечитывает определение по делу |
| GigaAM не мог загрузиться на службе | Библиотека берёт каталог только из аргумента `download_root`, а без него пишет в `~/.cache/gigaam`. Юнит работает с `ProtectHome=read-only`, и загрузка падала с `OSError [Errno 30]`. Переменная `GIGAAM_MODEL_DIR`, на которую мы рассчитывали, не читается никем |
| Отказ из-за прав был выдан за отсутствие интернета | Разбор шёл по склейке всех попыток, и в перечне доступных моделей из второй попытки нашлась подстрока `ssl`. Человек шёл проверять сеть, а дело было в каталоге. Теперь разбирается первая попытка — штатный путь загрузки, — а слова опознавания подобраны так, чтобы не совпадать с посторонним текстом |
| Предзагрузка весов качала не тот файл | `models.sh download` тянул снапшот с Hugging Face, а движок ищет `.ckpt` с CDN Сбера: команда отрабатывала успешно, место занимала, а движок всё равно шёл в интернет. Заодно скачанная модель показывалась незагруженной, а её размер — нулевым: поиск умел только раскладку каталогов Hugging Face |
| Поиск весов был скопирован в четырёх местах | Одна копия в сервере и три в `models.sh` — в `list`, `verify` и `remove`. Серверную поправили под новую раскладку GigaAM, три остальные остались знать только каталоги Hugging Face: скачанная модель показывалась незагруженной, её размер нулевым, а `remove` не удалял ничего. Копии сведены к одной |
| Репозиторий первой версии GigaAM отдавал третью | Передавалось голое имя `rnnt`, а библиотека сама разворачивает короткое имя в `v3_*`. Подмену по выводу не заметить |
| `lspci -s` мог оборвать определение оборудования | Карта могла исчезнуть с шины между обходом и уточнением имени — в виртуалке это обычное дело, — и ненулевой код обрывал бы определение целиком |

**Вход по логину и паролю**

Открыть интерфейс можно было только сходив на сервер за `api-key.txt` — ключ
удобен программе и неудобен человеку. Появились учётные записи: люди входят
логином и паролем, программы по-прежнему ходят с ключом, и ни одна
существующая интеграция от этого не меняется. По дороге закрыты два дефекта,
оба нашлись запуском.

| Что было | Чем грозило |
|---|---|
| Без ключа интерфейс отрисовывался целиком | Загрузка начиналась с каталога, а он открыт всем: страница выглядела рабочей, но очередь, результаты и настройки отвечали отказом на каждый запрос. Форма ввода ключа появлялась только при недоступном сервере. Теперь загрузка начинается с вопроса «кто я» |
| Кириллица в адресе обратного вызова ломала доставку молча | `urllib` требует уже закодованный путь и бросает «'ascii' codec can't encode characters», не дойдя до сети. Пять попыток подряд заканчивались пометкой «failed», а вызывающая сторона не получала ничего — при том что имя проекта в пути обратного вызова обычно как раз русское |

Как устроен вход: пароль хранится результатом scrypt с индивидуальной солью;
сессия в базе лежит не токеном, а его sha256, поэтому утёкшая база не даёт
войти; счётчик неудачных попыток и блокировка — в базе, а не в памяти
процесса, иначе перебор обходится через соседний экземпляр сервера; ответ на
неизвестный логин и на неверный пароль одинаков и приходит за одно и то же
время; смена пароля закрывает все чужие сессии; изменяющий запрос с чужим
`Origin` отклоняется вторым рубежом после `SameSite=Lax`; последнего
администратора нельзя ни разжаловать, ни отключить, ни удалить. Пароль по
умолчанию не просто вызывает предупреждение — до его смены сервер отвечает
отказом на всё, кроме самой смены. Забытый пароль восстанавливается из
консоли (`python3 -m asrhub --set-password`), причём с клавиатуры: аргументы
командной строки видны в списке процессов.

**Приём разговоров: ключ в теле запроса**

Совместимый клиент присылает ключ полем `api_key` внутри JSON, а не
заголовком. Разбирался только заголовок и параметр адреса — то есть
совместимость, ради которой раздел и делался, не работала на первом же шаге:
верный ключ давал 401.

**Раздел «Доступ» в настройках**

Ключ доступа и токен Hugging Face лежали в трёх разных местах и ни одно из
них не называлось «настройки»: список ключей — в «Сервере», поле для ключа
браузера — в «Справке», а токен нельзя было задать из интерфейса вовсе. Всё
собрано в один раздел настроек, и по дороге закрыты две вещи.

| Что было | Чем грозило |
|---|---|
| Токен Hugging Face задавался только при установке | Поменять его на работающем сервере можно было лишь правкой `config.yaml` руками. Теперь есть пара маршрутов `/api/settings/hf-token`: он не параметр каталога, поэтому через `PUT /api/settings` не проходит. Наружу отдаются шесть знаков и длина, целиком — никогда |
| Поле для ключа стояло в двух разделах | Оба читали одно значение из браузера: сохранив ключ в «Справке», человек видел в «Настройках» прежний до перезагрузки страницы |
| «Нет подходящей версии» не различало два разных случая | Пакет, у которого колёс ещё не собрали, и пакет, прямо запретивший эту версию Python, выглядят в выводе pip одинаково — а лечатся по-разному. Совет «подождите, выходят с задержкой» в втором случае просто неверен: ограничение стоит в метаданных. Разбор теперь читает строку `Requires-Python` и называет поддерживаемые версии |
| Движок считался установленным из-за чужой зависимости | Годилась любая строка файла требований, а `whisperx.txt` перечисляет ещё и `pyannote.audio` — тот стоит ради диаризации. Обновление принимало whisperx за установленный, пыталось обновить и падало каждый раз, пугая ошибкой на ровном месте |
| Проверка доступности жила только под `/api` | Балансировщики, `docker HEALTHCHECK`, uptime-мониторы и kubelet стучатся в `/health`. Появился короткий адрес с тем же ответом — и он же теперь отвечает `503`, когда база недоступна: прежняя проверка возвращала `200` серверу, который упадёт на первом же задании, то есть держала в строю заведомо нерабочий экземпляр. Пауза очереди при этом здоровьем не считается — это решение человека, а не поломка |
| Отказ приходил в двух разных видах | Ошибка через `error_response` уходила вложенной в `detail`, та же ошибка из глубины — полями верхнего уровня. Клиент был обязан разбирать оба вида, и нигде об этом не говорилось. Теперь поля есть верхним уровнем всегда, а `detail` сохранён — старые клиенты не ломаются |

### Десятый заход: прослушивание, аналитика, графики нагрузки

Заход начался не с обзора, а с трёх задач: дать слушать записи в разделе
результатов, довести аналитику и добавить в мониторинг картину по серверу и
видеокартам. Ревизия шла следом, по своему же свежему коду.

**Обновление и загрузка весов**

| Что было | Чем грозило |
|---|---|
| Один и тот же конфликт `protobuf` попадал в отчёт трижды | Два из трёх описывали состояние, которого к концу обновления уже не существовало. Отчёт, где две трети замечаний ложные, перестают читать целиком — вместе с третьим, настоящим |
| `protobuf` переустанавливался дважды за обновление | Между установками система проходила через состояние, в котором диаризация не работает: рантайм оказывался старше, чем gencode, и `ValidateProtobufRuntimeVersion` бросал `VersionError`. Проверено на настоящих окружениях: 5.29 + gencode 6.33.5 — отказ. Теперь версия закрепляется в `requirements/overrides.txt` и ставится один раз, после всех движков |
| Служба запускалась со старым юнитом | `systemctl` знал, что файл на диске изменился, и продолжал работать с прежним: переменные окружения для кеша моделей, только что прописанные обновлением, не действовали. Перезагрузка юнитов теперь делается сама, если `NeedDaemonReload` это подтверждает |
| GigaAM не грузился, а причина называлась неверно | Слово «ssl» из перечня доступных имён моделей попадало в разбор второй попытки и перебивало настоящую ошибку из первой: сервер сообщал «нет доступа к хранилищу весов» там, где домашний каталог был доступен только для чтения. Разбор идёт от первой попытки, а приметы сужены |
| `GIGAAM_MODEL_DIR` не читал никто | Переменная ставилась установщиком и юнитом, а библиотека о ней не знает: веса всё равно уезжали в `~/.cache/gigaam`, то есть под `ProtectHome=read-only` — никуда. Теперь каталог передаётся вызовом `download_root` |
| `models.sh download` качал не то, что потом ищет движок | Скачивался снапшот Hugging Face, а библиотека открывает `.ckpt` с CDN. На диске лежало одно, движок искал другое, и предварительная загрузка не помогала совсем |
| Репозиторий первой версии молча отдавал третью | Голое `rnnt` библиотека сама разворачивает в `v3_rnnt`. Подмена, которую по выводу не заметить: человек просил v1, получал v3. Незнакомый репозиторий теперь ещё и предупреждает о такой развёртке |
| Код состояния опознавался внутри пути | Приметы «401» и «403» были обычными подстроками и находились в `v3_rnnt-8401.ckpt` и в номере порта прокси: отсутствующий на диске файл сервер объявлял отказом в доступе к Hugging Face и отправлял чинить токен |

**Прослушивание записей**

| Что было | Чем грозило |
|---|---|
| Запись нельзя было послушать | Проверять расшифровку приходилось, скачав файл и открыв его сторонним проигрывателем — то есть глядя в текст и звук по отдельности. Появился `GET /api/jobs/{id}/audio` с поддержкой `Range`, проигрыватель в карточке и кнопка ▶ в списке результатов |
| Имя латиницей терялось при скачивании | `filename*=` по RFC 5987 сервер шлёт только для неascii-имён, а разбор в проигрывателе искал именно его: «record.wav» сохранялся как «запись-job_….wav». Разбор теперь общий с выгрузкой результатов |
| Половина принимаемых форматов не имела типа содержимого | В таблице стояло двенадцать расширений из двадцати девяти; про «.caf», «.w64» и «.m2ts» `mimetypes` не знает ничего, и браузер получал `application/octet-stream` — ответ, который он даже не пробует открыть. Это тот же отказ, только без объяснения |

**Аналитика**

| Что было | Чем грозило |
|---|---|
| Сводный отчёт читал архив двадцать раз | Каждый из девятнадцати разрезов делал свою выборку заданий. На сорока тысячах заданий отчёт собирался тринадцать секунд вместо двух |
| Окно у каждого разреза было своё | Границу считали от текущего времени в каждом разрезе отдельно. За секунды сборки она уезжала: «месяц» у последнего разреза начинался позже, чем у первого, — то есть разрезы одного отчёта не сходились между собой |
| Экономию от кеша считали двумя способами | В разрезе «эффективность» — по вбитой в код скорости 0.2, в разрезе «кеш» — по измеренной на своих же заданиях. На одной странице стояли два числа про одно и то же, различавшиеся вдвое |
| `LIGHT_COLUMNS` не отдавал пяти колонок | Метки, пик памяти, хеш файла и судьба уведомления молча приходили как `None`: новые разрезы считались по пустым данным и показывали нули как правду |
| Ход качества подписывался одной датой | Подпись оси была жёстко «день.месяц», а корзина на часовом окне — две с половиной минуты: двадцать четыре одинаковых подписи вместо оси |
| Пустой ход качества оставлял две дырки | Карточки нарисованы, внутри ничего и никаких объяснений |
| Пик памяти показывался как «23.4 тыс» | Общий формат чисел сокращает всё, что больше десяти тысяч. Под заголовком «Пик, МБ» это читалось как загадка; теперь «22.9 ГБ» |

**Мониторинг**

| Что было | Чем грозило |
|---|---|
| Раздел был целиком табличным | По таблице видно текущее значение и не видно ничего, ради чего мониторинг заводят: растёт ли нагрузка, упирается ли карта в предел мощности, совпадает ли провал скорости с ростом очереди |
| Вторая видеокарта для сервера не существовала | Сбор читал `splitlines()[0]` вывода `nvidia-smi`, то есть только первую карту. Температуры и потребления не было совсем, хотя они приходят тем же запросом даром — а без них «нагрузка на видеокарту» это загрузка в процентах и больше ничего |
| Ручка рядов читала в память всё окно | До тридцати тысяч строк на каждый опрос панели при открытом по умолчанию доступе к мониторингу. Свёртка перенесена в SQL: цену задаёт число точек графика, а не ширина окна |
| Таблица `gpu_samples` не чистилась никогда | Единственная таблица в базе без срока хранения, и растёт она кратно числу карт |
| Пропуск в ряду рисовался прямой | Остановка сервера выглядела на графике спокойным участком между двумя замерами — то есть график скрывал ровно то, ради чего на него смотрят |
| Корзина могла быть уже такта сборщика | Замеры приходят раз в двадцать секунд; в корзину такой же ширины то попадают два, то ни одного. Линия рвалась не там, где сервер молчал, а там, где такт разошёлся с границей корзины |
| Плотный ряд превращался в цепочку шариков | Точка — кружок с двухпиксельной обводкой цветом фона; когда соседи ближе обводок, они затирают линию между собой. Считать надо расстояние в пикселях, а не число точек |
| Пик памяти мерился не тем и не там | Счётчик спрашивался по `device` из настроек, где лежит «auto», сбрасывался после замера (стирая накопленное соседом по очереди) и считался даже когда рядом шло второе задание. Теперь устройство берётся у движка, счётчик обнуляется в начале, а замер делается только когда задание в очереди одно |

### Одиннадцатый заход: шесть пунктов из «стоит сделать»

Заход закрывал собственный список: шесть мест, где система работала, но
заметно хуже, чем могла бы. Плюс дефект, о котором сообщил владелец сервера
прямо по ходу работы, — и он оказался самым дорогим из всего списка.

**После обновления не обновлялся интерфейс**

| Что было | Чем грозило |
|---|---|
| На статике не было `Cache-Control` вовсе, а ссылки шли без версии | Starlette такой заголовок не ставит, а ответ без явного срока браузер волен держать по своему усмотрению — обычно десятую часть возраста файла. Для `app.js`, пролежавшего два месяца, это почти неделя, в течение которой браузер **не спрашивает сервер ни разу**: обновление проходило, файлы на диске менялись, а человек видел прежний интерфейс и не имел ни одного способа об этом узнать. Воспроизведено в настоящем Chromium: файл с давней отметкой времени, подмена содержимого обновлением, обычная перезагрузка — и старый скрипт из кеша, без единого запроса к серверу. Теперь ссылки несут отпечаток содержимого (`app.js?v=4decd2dd474a`), страница отдаётся с `no-cache`, а файлы с отпечатком — с годовым сроком и пометкой `immutable` |

**Поиск по расшифровкам**

| Что было | Чем грозило |
|---|---|
| Поиск шёл `text LIKE '%слово%'` | Ведущий шаблон не даёт воспользоваться индексом, поэтому редкое слово — ровно тот запрос, ради которого поиском и пользуются, — читало всю таблицу целиком: замерено 0.71 с на двадцати тысячах разговоров и росло линейно. Частое слово отвечало мгновенно только потому, что `LIMIT 50` останавливал перебор на пятидесятом совпадении. С указателем FTS5 тот же запрос на той же базе — 0.023 с, в тридцать раз быстрее |
| Результат не показывал, где нашлось | Список заданий отвечал «нашлось в этом разговоре» и замолкал; дальше человек открывал карточку и искал глазами — при том что сервер уже знал и фразу, и секунду. Теперь фраза стоит в строке результата, а щелчок по ней включает запись с этой секунды |
| Внутри разговора искать было нечем | Часовой разговор — это сотни реплик, и «найти, где обсуждали сроки» поиском по странице означает пролистать их все |
| Проверка «указатель уже собран» смотрела не туда | Первая версия считала строки самого указателя. У внешнего указателя `SELECT COUNT(*)` считает строки таблицы-источника и равен ему всегда, даже когда в указателе нет ничего: сервер уверенно решал, что архив проиндексирован, и поиск не находил ни одного старого разговора. Пустоту видно по теневой таблице `_docsize` |

**Действия над выборкой**

| Что было | Чем грозило |
|---|---|
| Все действия были поштучными | После обновления модели пятьсот разговоров переобрабатывались по одному, руками |
| — | Отказ на одном задании не отменяет остальных: в выборку почти всегда попадает что-то, к чему действие неприменимо, и прерывание всей команды означало бы, что пакетное действие работает только на идеально подобранной выборке. Права проверяются на каждом задании отдельно: иначе это способ удалить чужой архив, зная только номера |
| Удаление задания было написано дважды | Одиночная ручка и пакетная разошлись бы: одна забыла бы файлы, вторая — записи. Обе зовут одну функцию, и на это есть проверка |

**Пик памяти**

| Что было | Чем грозило |
|---|---|
| Замер делался, только когда задание в очереди одно | Счётчики памяти общие на процесс, и при двух заданиях цифра не относится ни к одному. Но отсюда следовало, что на сервере с двумя воркерами — то есть там, где вопрос «хватит ли карты» и стоит, — раздел «Ресурсы» оставался пустым всегда. Теперь мерим всегда, а рядом пишем, сколько заданий шло разом: «при двух заданиях карта поднималась до 27 ГБ из 32» — это и есть ответ для планирования |
| Одновременность считалась бы по концам задания | Всплеск в середине — ровно тот случай, когда памяти и не хватает, — не попал бы ни в одну из двух точек. Отметка обновляется при каждом изменении состава работающих |

**Выгрузка аналитики**

| Что было | Чем грозило |
|---|---|
| Отчёт можно было только смотреть | Чтобы отдать месячные числа руководителю или в бухгалтерию, их переписывали руками — и переписывали с округлённых значений на экране, а не с тех, что посчитал сервер |
| — | CSV собирается с точкой с запятой и меткой порядка байтов: «правильный» файл с запятыми Excel с русскими настройками показывает одной колонкой кракозябр, то есть выгрузка есть, а воспользоваться ей нельзя |

**Обслуживание по расписанию**

| Что было | Чем грозило |
|---|---|
| Копия базы была строкой в `cron` из главы «Эксплуатация» | То есть ручной настройкой, о которой надо сначала узнать. Сервер теперь умеет сам — тем же способом, каким советует человеку: командой SQLite `.backup`, а не копированием файла, которое на работающей базе в режиме WAL даёт несогласованный результат |
| Восстановления не было вовсе | `service.sh restore` проверяет копию до того, как тронуть рабочую базу: битый файл, обнаруженный после подмены, оставил бы вообще без базы. Прежняя база и её журнал сохраняются рядом — восстановление не из той копии обычная ошибка, и она должна быть обратимой |
| Сводки о работе не существовало | Тревоги срабатывают на происшествия, а «как шли дела в целом» приходилось смотреть самому. Сводка уходит на заданный адрес и несёт поле `text`: приёмник входящих сообщений в мессенджере показывает именно его, и в чат приходит читаемый отчёт, а не свёрнутый JSON |
| Негодный адрес в настройках ронял отправку до отправки | `urllib` бросает на сборке запроса, а не на соединении, и это было вне защиты: служебный цикл писал бы ошибку в журнал каждые двадцать секунд |

**Найдено по дороге**

| Что было | Чем грозило |
|---|---|
| Новая колонка появилась без поднятия номера версии схемы | Забыли — и колонка не добавляется, а каждый запрос к таблице падает с «no such column» на боевом сервере. Так и случилось прямо в этом заходе. Теперь набор колонок сверяется при каждом запуске, а не только при смене номера: проверка стоит одного `PRAGMA table_info` по нескольким таблицам |
| Правка в собираемой главе документации исчезала | Четыре главы собираются из каталога, и правка прямо в файле живёт до первой сборки. Именно это и произошло с разделом про графики нагрузки: он пропал из PDF молча. Теперь об этом говорит тест, а не пропавший раздел |

### Двенадцатый заход: ревизия того, что сделали десятый и одиннадцатый

Заход не добавлял возможностей — он искал дефекты, в том числе в коде,
написанном двумя предыдущими. Такие находки самые неприятные: возможность
объявлена работающей, и никто больше на неё не смотрит. Из четырнадцати
находок шесть — в собственном свежем коде.

**Недоверенный ввод и разграничение**

| Что было | Чем грозило |
|---|---|
| `call_id` из запроса становился частью пути | Приём разговоров складывает скачанную запись как `<загрузки>/<call_id>_<часть>-<имя>`. Значение вида `../../../имя` уводило файл за пределы каталога загрузок, а расширение задавал адрес источника: обычный ключ мог положить свой `.js` или `.html` куда угодно, куда пишет служба, — например в каталог статики, откуда сервер отдаёт интерфейс. Тот же `call_id` попадал в путь, который потом рекурсивно удаляется при уборке. Воспроизведено: `/var/lib/asrhub/uploads/../../../подброшено_1-y.js` → `/var/подброшено_1-y.js` |
| Удаление задания снимало файл по значению из базы без проверки | Для выдачи записи наружу проверка вложенности в каталог написана и подробно обоснована, а на пути удаления её забыли. В связке с предыдущим — удаление произвольного файла. Та же дыра была и в уборке по сроку хранения, которая идёт раз в час и молча |
| `GET /api/settings` отдавал адрес обратного вызова и всю раскладку каталогов любому ключу | Входящий адрес чата (Slack, Teams) несёт токен прямо в адресе: кто его знает, тот пишет в чат от имени сервера. Раскладка каталогов — разведка перед атакой, и соседний `GET /api/system` прячет её за правами администратора с этой же мыслью; здесь она уходила ключу «только чтение», что делало ту защиту бессмысленной |
| `GET /api/monitoring/targets` отдавал адреса приёмников целиком | У InfluxDB и Pushgateway учётные данные сплошь и рядом стоят в строке запроса. Соседние «заменить» и «проверить» требуют администратора, а чтение — нет. Теперь неадминистратор видит схему и узел (куда шлём — вопрос законный), но не путь и не параметры |

**Свой же свежий код**

| Что было | Чем грозило |
|---|---|
| Аналитика падала с 500 у любого ключа с группой | Ключ в подразделении видит задания всей группы, и разграничение отдаёт для него список владельцев. | Кеш выборок был общим на все потоки | Объект аналитики один на приложение, обработчики синхронные и живут в пуле потоков. Тот же случай — «asrctl backup» руками одновременно с заходом по расписанию |
| Разрез по меткам ничем не ограничен | Метку задаёт клиент, и её мощность — единственная в отчёте, которую сервер не контролирует. Клиент, ставящий уникальную метку на каждое задание, превращал разрез в сто тысяч строк — и в таблице, и в листе выгрузки, где остальные разрезы не длиннее полусотни |

**Очередь и служебный цикл**

| Что было | Чем грозило |

Экземпляр, застрявший дольше отметки жизни, оживал и писал свой отказ поверх задания, которое уже считает сосед; когда сосед досчитывал, его защищённая запись не проходила, и **готовая расшифровка выбрасывалась**. Сервер жил с половиной заявленных до перезапуска, показывая в состоянии полное число |
| Ограничитель записей в журнале не включался никогда | Сбой шага ловился вложенным `except`, внешний блок завершался штатно, и ветка «иначе» объявляла восстановление и обнуляла счётчик. И «восстановился» было неправдой |
| Доставка уведомлений не смотрела на остановку | Пять попыток с паузами до минуты, потоки не демоны: процесс не завершался ещё полторы минуты после «Очередь остановлена», а при недоступном приёмнике до полутора минут на каждое уведомление. Отправка после остановки заводила новый пул, который уже некому гасить |
| Задание из кеша теряло два счётчика | Знаки и говорящие не переносились. Строка «Знаков» в сводке занижалась ровно на долю попаданий в кеш — при том что «Слов» считалось полностью, так что расхождение выглядело как ошибка в подсчёте, а не как пропуск. Ноль говорящих вдобавок молча выбрасывал такие задания из разреза по числу собеседников |

### Тринадцатый заход: аналитика записей

Заход добавлял раздел, а не чинил старое, — и дефекты здесь почти все
свежие, из кода, написанного в этом же заходе. Такие находки самые
неприятные: возможность объявлена работающей, и никто больше на неё не
смотрит.

**Разбор содержания**

| Что было | Чем грозило |
|---|---|
| Оценка тональности обрезалась по ±1 | Средний вес делился на 2 и подрезался, а веса словаря доходят до ±2 — то есть всё от −2 и ниже давало ровно −1. На корпусе в две тысячи разговоров в границы упиралась почти половина записей: список «самые тяжёлые разговоры» получался из шестисот штук с одинаковой оценкой −1,00, то есть выбранных как попало. Усилитель при этом не значил ничего — «плохо» и «очень плохо» давали одно число. Заменено на плавное сжатие: порядок сохраняется на любых весах, а калибровка сдвинулась с 0,50 на 0,46 |
| Пункт скрипта «Представился» искал среди примет голое «это» | «Алло, это опять вы?» засчитывалось как представление оператора. Примета, совпадающая с одним из самых частых слов языка, делает пункт выполненным всегда, а разрез соблюдения скрипта — постоянной единицей. Нашлось на снимке экрана для документации: в столбце «что нашли» стояло «это». Та же беда была у пункта «Подтвердил понимание» со связкой «то есть» |
| «Уточню» стояло в пункте «Подтвердил понимание» | Основа общая с «уточнить», и пункт срабатывал на «хотел уточнить по заказу» — то есть на реплике клиента. Переехало в «Назвал следующий шаг», где ему и место: это обещание сходить и посмотреть, а не переспрос |
| Оператор нигде не определялся | Настройка обещала: «пусто — определять самостоятельно, оператор здоровается первым». Кода за этим обещанием не было, и разрез по операторам показывал одну строку «—» на весь архив |

**Что нашла ревизия раздела**

Две трети находок этого захода — из ревизии, проведённой после того, как
раздел был собран и объявлен работающим. Половина из них — в собственном
свежем коде, и это как раз тот случай, о котором сказано выше: возможность
объявлена работающей, и никто больше на неё не смотрит.

| Что было | Чем грозило |
|---|---|
| Пересчёт всего архива обходил проверку прав | `if задания:` было истинно для непустого списка, отбор по владельцу оставлял пустой, а `recompute([])` уходил в ветку «весь архив»: строка `require_admin` не выполнялась никогда. Любой ключ одним запросом со списком из одного несуществующего задания сбрасывал разбор всех записей сервера, включая чужие, — и мог повторять это в цикле |
| На POST-маршрутах раздела не было `require_write` | Ключ, выданный «только на чтение», пересчитывал разбор; соседние маршруты заданий эту проверку делают все до одного |
| `GET` карточки писал в три таблицы | Причём делал это и ключом «только чтение», и при выключенной настройке `content_analysis`: «не разбирать содержание» ничего не выключало, а запись на GET может вызвать даже предзагрузка ссылок в браузере |
| Слова-паразиты считались по основам | Основа паразита совпадает с основой обычного слова: «так» ловило «такая», «просто» — «простой», «слушай» — «слушаю». На вежливой реплике «я вас слушаю, скажите, пожалуйста» доля паразитов выходила 0,24 при пороге вывода 0,04 — хуже всех выглядел оператор, делающий ровно то, чего требует скрипт |
| Отрицание переходило границу предложения | Окно смотрит на три слова назад и точки не видело, а оценка записи считается по склеенному тексту всего разговора: «Никаких претензий. Спасибо, помогли!» получало −0,23 «отрицательная», а отрицание из реплики клиента переворачивало похвалу в реплике оператора |
| Утверждения засчитывались вопросами | «Как я уже сказал…», «Что касается доставки…», «Сколько нужно, столько и сделаем» — соотносительные обороты начинаются теми же словами, что и вопросы. Четыре утверждения из четырёх шли в счёт вопросов |
| «Судя по всему» попадало в тревожные упоминания | Основа «суд». Оборот из каждого второго разговора поддержки поднимал запись в список «послушать срочно» |
| Десятичная дробь становилась датой | «Счёт на 1.5 миллиона» → первое мая, «скидка 2.5 процента» → второе мая. Обещанию приписывался срок, и разрез «обещания без названного срока» молчал ровно там, где должен сработать. Туда же «через курьера» и «через нашего менеджера»: предлог «через» в русском чаще не про время |
| Отсечка редких основ поднимала опечатки наверх | Основа, не попавшая в словарь частот, получала `df = 0` — то есть самую большую редкость и самый большой вес во всём корпусе. Отсечка, заведённая против опечаток распознавания, ставила их на первое место |
| Свод считался выборкой в память с пределом | На архиве в сто тысяч записей окно «месяц» упиралось в предел: показатели считались по свежей половине и подавались как показатели месяца, а прошлому периоду доставалось четыреста пятьдесят записей вместо пятидесяти тысяч. Переписано на группировку в базе |

### Четырнадцатый заход: развёртывание в контейнере и проверки браузером

Заход начался с вопроса «что ещё доделать» и свёлся к двум местам, которые
до сих пор проверялись глазами: пути установки в контейнер и самого
интерфейса.

**Путь Docker.** Демон в этот раз поднялся, но реестры образов закрыты
сетевой политикой среды, и базовый слой не тянется — то есть `docker build`
снова не выполнялся. Зато выполнялось всё остальное: файлы Compose
разбираются настоящим `docker compose config`, установка в режиме docker
проходит целиком с подменённым `docker`, а команда выбора движков из
`Dockerfile` вынимается из файла и исполняется как обычный shell — с
подменой `pip` на запись в файл. Так и нашлось нижеследующее.

| Что было | Чем грозило |
|---|---|
| Ключ `--engines` не доходил до образа | Установщик писал список в `docker/.env`, показывал его человеку строкой «Движки: gigaam,vosk» — и собирал набор профиля: образ про эту переменную не знал. Человеку говорили одно, в контейнер попадало другое |
| `--host 127.0.0.1` в режиме docker не значил ничего | Адрес писался в `.env`, а Compose знал только про порт и публиковал его на всех интерфейсах. Установка «только для себя» выставляла сервер в сеть — и узнать об этом было неоткуда |
| Профиля `apple` в образе не было | Ветка `case` его не знала, и он проваливался в умолчание — один faster-whisper вместо трёх движков, молча |
| Наборы движков образа и установщика разошлись | `full` при обычной установке даёт десять движков, в образе было семь — без `tone`, ради которого заводился профиль `russian`. Ни один из двух списков не знал о существовании второго. Теперь намеренные расхождения записаны в `Dockerfile` строками «ИСКЛЮЧЕНО-В-ОБРАЗЕ» и «ДОБАВЛЕНО-В-ОБРАЗЕ», а тест разбирает оба списка и сверяет |
| `overrides.txt` в образе не применялся | Движки ставятся по одному, каждый своим вызовом pip, и последний перетягивает общие пакеты на себя; при обычной установке версии возвращает `apply_overrides`, в образе этого шага не было. Для профиля с диаризацией это ровно тот случай, ради которого файл и заведён: protobuf отказывается грузить код, сгенерированный более новой версией, и движок падает на импорте |
| Версия в метке образа вписана числом | `org.opencontainers.image.version="3.0.0"` рядом с файлом `VERSION`, где то же число. Разойтись они могли молча — и `docker inspect` показывал бы прошлогоднюю версию. Теперь метка берётся из аргумента сборки, а тест сверяет его умолчание с файлом |
| `--dry-run --mode docker` писал на диск | Дописывание `ASRHUB_UID` в `.env` шло мимо `write_file` и потому не подчинялось пробному запуску: при переустановке поверх существующей пробный запуск менял настоящий файл, а на чистой машине падал с «No such file or directory». Пробный запуск не имеет права менять ничего |
| `--dry-run --mode docker` заканчивался ошибкой | Переход в каталог стоял вне обёртки `run` и выполнялся по-настоящему — в каталог, которого при пробном запуске ещё нет. То есть пробный прогон установки в контейнер не работал никогда |

**Проверки интерфейса.** Заведены проверки настоящим браузером — тринадцать
штук, Playwright. Проверяется не вёрстка (её сравнение со снимком ломается
от любой правки отступа и через месяц отключается целиком), а то, что
ломается по-настоящему: чиста ли консоль, нарисовалось ли то, за чем
пришли, и не осталось ли на экране следов предыдущего раздела.

| Что было | Чем грозило |
|---|---|
| Проверка гонки вкладок проходила и на сломанном коде | Задержка ответов делалась обработчиком `page.route` с `time.sleep`, а он в синхронном Playwright исполняется в потоке команд теста: останавливались не только запросы, но и всё общение с браузером. Клик по второй вкладке доезжал уже после того, как первая дорисовалась, порядок событий выходил правильный сам собой — и проверка была зелёной со снятой защитой. Проверено прямо: защиту сняли, тест не упал. Задержка перенесена внутрь страницы подменой `fetch`; теперь снятие защиты роняет проверку, как и должно |
| Отбор по содержанию обрезался посреди слова | При жёсткой ширине поля самый длинный отбор показывался как «с упоминанием суда и жало» — выбранное значение прочитать было нельзя. Нашлось на снимке экрана для этой самой документации |

Отдельно проверено, что новые проверки что-то проверяют: для каждой правка
откатывалась и прогон повторялся. Семнадцать проверок — тринадцать на файлах
развёртывания, из них шесть исполняют команду выбора движков как shell, и
четыре на самом установщике — падают, когда дефект возвращается. Ни одна не
осталась зелёной на сломанном коде; проверка гонки вкладок до этого как раз
оставалась.

### Пятнадцатый заход: первый этап развития аналитики по мировому опыту

Заход начался с разбора того, что считают ведущие системы речевой
аналитики и мониторинга распознавания — облачные API, контакт-центры,
аналитика продаж, российский рынок, эксплуатация ASR, — и сверки с тем, что
есть здесь; разбор лежит отдельным документом. Из пятидесяти предложений
в первом этапе сделано то, для чего данные уже лежали в базе.

**Доложено.** Стороны разговора — доля речи оператора, его самый долгий
монолог против рассказа клиента, смены говорящего, пауза перед ответом,
наложение речи в секундах, заметная тишина, соотношение темпов — и
смешанная тональность как четвёртый класс. Пауза перед ответом считалась с
первой версии разбора и не показывалась нигде. Признаки раздражения
клиента и повторного обращения, нецензурная лексика выключенным по
умолчанию словарём, окно пункта скрипта в секундах, новые слова периода,
удаление записей по требованию и отметка согласия. Здоровье распознавания:
галлюцинации Whisper по порогам самого Whisper, невозможный темп, повторы,
известные фразы, разметка говорящих — по сегментам, без эталона; данные для
этого сервер хранил с десятой версии схемы и не смотрел на них ни разу.

**Что нашлось по ходу.** Дефекты здесь — в свежем коде этого же захода,
и находились они тем же порядком: воспроизвести запуском, починить, закрыть
регрессией, откатить правку и убедиться, что регрессия падает.

| Что было | Чем грозило |
|---|---|
| Ручка списка заданий отвергала отборы по здоровью распознавания | Проверка ключа шла только по перечню отборов содержания; «подозрительная расшифровка» есть и там, где разбор содержания выключен, — и ручка отвечала «неизвестный отбор», хотя база его знала. Нашлось на снимке экрана: интерфейс получал 400 |
| Пересчёт одной записи не пересчитывал признаки качества | Их считали только распознавание и фоновый разбор архива; после смены ожидаемого числа говорящих пришлось бы ждать фонового прохода, который эту запись уже прошёл |
| Список исключений словаря мата не срабатывал ни разу | Он сравнивался по точной форме, а корни — по началу слова: «херувима» корень ловил, а исключение «херувим» не спасало. Проверка мутацией показала, что список можно удалить целиком и ни один тест не заметит; теперь исключения — тоже по началу слова, и тест это видит |
| Проверка «повторное обращение» не отличала порог новизны | Слово из одной записи не проходило порог тем вообще, и правило «от трёх записей» можно было выкинуть незаметно; проверка переписана на слово из двух записей — оно проходит порог тем и не проходит порог новизны |
| Один и тот же порог объявлялся в модуле скрипта дважды | След от восстановления файла из резервной копии в прошлом заходе: безвредно, но второе объявление молча переопределяло первое |
| Вывод про тональность группы называл числа с четырьмя знаками | «−0,2122 против 0,1734» рядом со сводом, где два знака: вывод выглядел посчитанным по другим числам |
| Обрезка примет разбора при выключенном словаре | Выключенный словарь мата всё равно искал и складывал найденное в подробности записи — то есть «выключено» не было выключено. Найдено мутацией: проверка проходила и с убранным условием |

Проверки этого захода — восемнадцать новых в `tests/test_content.py`, и
девятнадцать правок откатывались для мутационной проверки; после того как
три проверки, пропустившие свою мутацию, были переписаны, ни одна регрессия
не осталась зелёной на сломанном коде.

### Шестнадцатый заход: категории обращений — движок правил

Второй этап плана по мировому опыту начинается с самого большого куска:
движка правил, который закрывает и категории обращений, и стоп-слова
оператора, и возражения с их отработкой. В этом заходе — сам движок,
категории с готовым набором, счёт и динамика; балл оператора и трекеры —
следующими заходами на той же основе.

**Доложено.** Правила над словами расшифровки — `И`, `ИЛИ`, `НЕ`,
`РЯДОМ(N)`, скобки, фразы по основам и точные в кавычках — с пределами
Genesys (двадцать операндов, три уровня скобок) и ошибками с позицией в
строке. Категория — правило плюс «кто сказал» и «где в разговоре» с окном в
секундах; вид категории — обращение, нарушение оператора, возражение,
отработка. Совпадения лежат отдельной таблицей `content_hits`, по ней база
считает долю, изменение к прошлому периоду, растущие и угасающие категории
и число записей без единой категории — точно, а не оценкой. Готовый набор из
десяти категорий действует, пока не сохранён свой; редактор проверяет
черновик на настоящей записи и подсвечивает ошибку правила под строкой;
настройка с ошибкой в базу не попадает. Отбор по категории в «Результатах»,
блок в карточке записи, выводы, сводка по расписанию и лист выгрузки.
Скрипт разговора стал частным случаем категории: список примет — это
«ИЛИ», и проверяет его тот же движок, а пункту доступно поле `rule` с
остальными операторами.

**Что нашлось по ходу** — в свежем коде этого же захода:

| Что было | Чем грозило |
|---|---|
| Одно слово записи считалось дважды | «оплата ИЛИ оплатить» сводится к одной основе, и первый же прогон насчитал четыре совпадения на трёх словах: каждая примета засчитывала то же слово отдельно. Совпадения теперь сливаются по отрезку слов, и проверка требует ровно одного |
| Ошибка разбора называла оператор по-английски и не с той позиции | «оператор без операнда: «OR»» на правиле с «ИЛИ», а позиция обрыва считалась по служебному кортежу, а не по тексту. Редактор подсвечивал не то место |
| Карточка записи повторяла реплику по разу на каждую примету | «Срок поставки сорван» стояла дважды — под «срок» и под «сорван». Видно на снимке экрана; теперь одна реплика — одна строка со всеми приметами |
| Проверка «без категории» пропускала мутацию | Счёт «без категории» обязан смотреть только категории обращений, не нарушения; корпус проверки состоял из одних обращений, и убранное условие по виду категории не ломало ничего. Проверка дописана записью с одним нарушением |
| Ожидание проверки расходилось с разбором слова | Проверка ждала, что «бракованный» найдётся по «брак»; основы у них разные («бракова» и «брак»), и это как раз причина, по которой в готовом наборе стоят оба слова. Дефект в проверке, не в коде |

Десять новых проверок в `tests/test_content.py` и три в браузере; одиннадцать
правок откатывались для мутационной проверки — окно `РЯДОМ`, слияние
совпадений, фильтр говорящего, окно в секундах, время первого совпадения,
подразумеваемое «И» перед «НЕ», отбор по категории, порог роста, точные
формы, удаление совпадений с заданием и счёт «без категории»; последняя
и была той, что прошла, пока проверку не дописали.

### Семнадцатый заход: категория × показатели, драйверы, трекеры, возражения

Вторая половина второго этапа — то, что становится возможным, когда
категории уже лежат в базе.

**Доложено.** Разрез «по категориям обращений» — те же показатели, что у
владельцев и меток, через соединение с таблицей совпадений, с подписями и
видом из набора; участвует в выводах о группах против среднего и в
выгрузке. Драйверы негатива — подъём категории среди отрицательных
разговоров к её частоте вообще, с порогами 1,25 и десять записей и с
честной подписью «связь, не причина»; вывод называет оба числа. Трекеры:
флаг «сообщать» у категории пишет событие в журнал и шлёт POST на
`tracker_url` сразу после распознавания — отдельным потоком, с той же
проверкой адреса, что у обратного вызова, и никогда при пересчёте архива;
счёт срабатываний — по журналу, в сводке и метрикой. Возражения без
отработки: пара видов «возражение — отработка» в готовом наборе, окно в
три реплики, NULL вместо нуля там, где отработку считать нечем; колонки в
своде, отбор, метрика, строка сводки, блок в карточке. Метрики категорий —
по метке на категорию.

**Что нашлось по ходу.** Дефектов в коде этот заход не выявил — проверки
писались до кода, и семь мутаций (окно отработки, счёт «без ответа» без
категорий отработки, перевёрнутый подъём, снятый порог записей, флаг
«сообщать», проверка адреса, вид категории в разрезе) упали каждая. Два
изменения в существующих проверках: метрики содержания получили метки, и
проверка «каждая метрика описана в каталоге» сверяла имя вместе с
метками — исправлена, заодно проверяет, что HELP и TYPE стоят один раз на
имя; версия разбора в двух проверках была записана числом, а не
константой модуля.

### Восемнадцатый заход: балл оператора, штрафы, стоп-слова, эмпатия

Последняя часть второго этапа — оценка оператора одним числом, которое
можно проверить.

**Доложено.** Вес у пункта скрипта и штраф у категории; балл 0–100 как у
Verint и Google — веса выполненных к сумме всех минус штрафы, за категорию,
а не за совпадение, с краями 0 и 100 и без балла там, где нет пунктов
скрипта. Стоп-слова оператора — готовая категория вида «нарушение» со
штрафом 10, только у оператора, по точным формам. Индекс эмпатии по
формуле Genesys — (вежливых − невежливых) ÷ сумму — по репликам оператора,
со словарём невежливых оборотов и None вместо нуля, когда оборотов нет.
Колонки, разрез по операторам с тремя новыми столбцами, три отбора,
выводы, сводка, выгрузка, три метрики с порогами из каталога, поля в обоих
редакторах, ряд в карточке записи и в своде.

**Что нашлось по ходу.**

| Что было | Чем грозило |
|---|---|
| Проверка весов не отличала взвешенный балл от простого | В первой редакции проверки веса 3, 1 и 2 при двух выполненных из трёх давали те же две трети, что и без весов; мутация «веса игнорируются» проходила. Веса заменены на 3, 1 и 4 — половина против двух третей |
| Таблица разрезов перестала помещаться | С тремя новыми столбцами последний уезжал за край карточки, и на снимке экрана «нарушения» не было видно. Убран столбец «обещаний без срока» (он есть в своде), заголовки укорочены |

Четыре новые проверки (778 всего); шесть мутаций — штраф за совпадение,
снятый нижний край балла, игнорирование весов, эмпатия по всем репликам,
нарушения счётом совпадений, стоп-слова у любого говорящего — упали каждая.

### Девятнадцатый заход: карточка оператора, коучинг, эталоны, обращение по имени

Первая половина третьего этапа — всё, что раздел знает о сотруднике, в
одном месте.

**Доложено.** Вкладка «Операторы» с переключателем «говорящий /
владелец»; карточка против команды с четырнадцатью показателями,
вердиктом по направлению и прошлым периодом того же оператора; балл и
тональность по неделям; нарушения по категориям; лучшие и худшие записи.
Очередь коучинга с восемью причинами и отметкой «разобрано», эталонные
разговоры с отметкой «эталон»; отметки — в своей таблице, переживают
пересчёт, пишут событие в журнал. Обращение по имени — словарь из двухсот
с лишним имён с формами склонения и звательными, без имён-омонимов и
форм, совпадающих с «ИНН», «лиды», «марка»; пункт скрипта нового вида —
проверяемый по факту, а не по словам.

**Что нашлось по ходу.**

| Что было | Чем грозило |
|---|---|
| «Добавить пункт» в редакторе скрипта не добавлял ничего | Кнопка дописывала пункт в черновик и перерисовывала вкладку, а вкладка заново читала скрипт из настроек — черновик с новым пунктом терялся. Так было с тринадцатого захода; проверка в браузере правила примету, но пункт не добавляла. Нашлось на снимке экрана для этой главы: снимать было нечего. Пункт теперь дорисовывается на месте, проверка добавляет и обычный пункт, и «по имени» |
| Проверка карточки оператора проходила на сломанном коде — из-за байт-кода | Мутация «вердикт перевёрнут» правила строку той же длины, и после восстановления файла в ту же секунду Python считал старый `.pyc` действительным: в кеше остался мутант, и честный код падал на проверке. Кеш байт-кода теперь чистится перед каждым прогоном после мутаций; сам код был верен |
| Основы имён не годились для словаря | Стеммер даёт «Иван» и «Ивану» разные основы, а «Анна», «Оля», «Елена» — двухбуквенные, под которые попадает половина слов. Словарь переписан на формы склонения до того, как попал в поставку; проверка сличает и падежи, и звательные, и омонимы |

Четыре новые проверки (784 всего), семнадцать в браузере; шесть мутаций —
собственное имя оператора, проверка по факту, скрытие разобранных, эталоны
с нарушениями, вердикт, фильтр оператора — упали каждая.

### Двадцатый заход: нормы от своего архива, дрейф уверенности, контрольные карты

Вторая половина третьего этапа — статистика, которой раздел до сих пор
не имел: не «ориентир из чужой методики», а «как обычно бывает здесь».

**Доложено.** Модуль `stats.py` без сторонних зависимостей: процентили с
линейной интерполяцией, медиана и межквартильный размах с границами по
Тьюки, двухвыборочный критерий Колмогорова — Смирнова с асимптотическим
p-значением (сверен со scipy на трёх парах выборок), пределы контрольных
карт 2σ/3σ и правило серии из семи точек. Нормы от четырёх недель до
периода в таблице свода со статусом периода по медиане; контрольные
карты по дням для доли отрицательных, балла, тональности и скрипта — и
для уверенности, низкой уверенности и подозрительных сегментов в
«Аналитике»; дрейф уверенности по моделям с порогами Deepgram, тремя
метриками и строкой в сводке только при вердикте.

**Что нашлось по ходу.**

| Что было | Чем грозило |
|---|---|
| Число дней периода считалось округлением вверх | Конец окна вычислялся на доли секунды позже начала, и «неделя» давала восемь корзин: последняя — пустая точка в будущем, которая читалась как «день без записей» |
| Правило «предупреждение при 2σ» первой редакции срабатывало на одинаковых выборках | Сравнивалось со стандартной ошибкой среднего, а не с разбросом: на двухстах заданиях любое случайное расхождение средних превышало её. Правило переписано на связку «p < 0,05» и «сдвиг 10 %», как у Deepgram; одинаковые выборки дают «без дрейфа» |
| Хвост статистики KS после исчерпания одной выборки | Строка была лишней: расхождение после этого только убывает. Нашлось мутационной проверкой — единственный эквивалентный мутант захода; строка убрана, чтобы не держать мёртвый код |
| Дрейф и контрольные карты в сводном отчёте читали архив со своей границей | Проверка одиннадцатого захода «все разделы одного отчёта — одно окно» упала на первом же полном прогоне: у новых разделов появилось второе окно — четыре недели базы до периода. Окно законное, но проверка требовала ровно одного. База теперь отсчитывается от той же замороженной границы, что и у остальных разделов, а проверка допускает второе окно только на ровно двадцать восемь дней раньше первого — и переводит часы на секунду вперёд при каждом обращении, чтобы раздел, считающий границу сам от «сейчас», не совпал с общим по случайности |
| Дрейф за «всё время» показывал «период» из последних четырёх недель | Границы у «всего времени» нет, и база отсчитывалась от текущего момента: «текущей» выборкой оказывались последние двадцать восемь дней под именем всего архива. Теперь без границы нет и базы: выборка — весь архив, вердикт — «мало данных» |

Четыре новые проверки (788 всего), восемнадцать в браузере; семь мутаций
— правило Тьюки, прерывание серии пропуском, вердикт без порога сдвига,
база нормы из того же периода, тревога на сдвиг вверх, своя граница у
дрейфа и своя у контрольных карт — упали каждая.

### Двадцать первый заход: точность по эталону, калибровка уверенности, латентность

Первая часть четвёртого этапа — здоровье распознавания там, где его можно
доказать, а не заподозрить: по записям с эталоном.

**Доложено.** MER и WIL рядом с WER (Morris, 2004): MER ограничен единицей,
разрыв WER − MER — мера вставок, то есть галлюцинаций; срезы точности по
модели, длительности, источнику и языку сложением слов, а не усреднением
записей, с порогом значимости в десять тысяч слов. Калибровка уверенности:
выравнивание по словам, десять корзин, ECE, AUC и диаграмма надёжности —
считается один раз при задании эталона и складывается в запись. Латентность:
p50/p95/p99 времени обработки и RTF по моделям и длительности, поток —
секунды до первого текста, которые сессия теперь пишет в метрики. Вкладка
«Эталон» в карточке записи с подсветкой расхождений; три раздела аналитики,
четыре листа выгрузки, пять метрик мониторинга с порогами.

**Что нашлось по ходу.**

| Что было | Чем грозило |
|---|---|
| Эталон, заданный после распознавания (`POST /api/jobs/{id}/reference`), сравнивался с текстом задания вместе с метками говорящих | Тот же дефект, что был исправлен в конвейере в пятом заходе, — но только там: каждая реплика «Говорящий N:» приносила две вставки, и один и тот же эталон давал два разных WER в зависимости от того, когда его задали. Найдено воспроизведением на записи с разметкой; теперь оба пути сравнивают по сегментам |
| Задание с эталоном, отданное из кеша, оставалось без точности | Клон переносил текст и сегменты, но не считал WER по своему эталону и не переносил признаки подозрительности: в срезах точности таких записей не было, а в отборе «подозрительная расшифровка» — тоже |
| Проверки мониторинга считали именем метрики только буквы | `asrhub_rtf_p95_by_model` читалось как `asrhub_rtf_p`, и правило поверх новой метрики падало как «неизвестное»; выражение поправлено на буквы и цифры |
| Выравнивание для калибровки дополнительно считало матрицу Левенштейна внутри промежутков difflib | Мутационная проверка показала, что это мёртвый код: без отсева «мусора» промежуток по построению не содержит общих слов, и точный расчёт внутри него ничего не находит. Убрано вместе с ложным пояснением |
| Проверка эталона дважды ошибалась в собственных ожиданиях | Демонстрационный движок каждый раз выдаёт новый текст, и «одинаковые» записи не одинаковы; клон из кеша повторяет то задание, с которым совпали настройки, а не последнее. Обе поправки — в проверке, не в коде |

Восемь новых проверок и одна в браузере (797 всего, девятнадцать в
браузере); девять мутаций — усреднение вместо сложения слов, знаменатель
MER, граница корзины, слагаемое ничьих в AUC, кеш в латентности, первый
текст потока, эталон у клона, метки говорящих в ручке эталона — упали
каждая; одна оказалась эквивалентной и убрана.

### Проверено не было

**1. Образ Docker не собирался.** Все известные дефекты развёртывания
исправлены и проверены тем, чем можно проверить без сборки: конфигурации
Compose разбираются настоящим `docker compose config` для всех
задокументированных команд, `nginx -t` принимает конфигурацию прокси (а
старую — отвергает), `bash -n` проходит по entrypoint, установка в режиме
docker выполняется целиком с подменённым `docker` — и доходит до `build` и
`up -d` с правильными аргументами, — а команда выбора движков вынимается из
`Dockerfile` и исполняется как обычный shell с подменой `pip`.

**2. Выравнивание MFA не проверено на реальных весах.** Раскладка слов теперь

**1. Поиск по расшифровкам — на индексе, а не перебором.** Сейчас `search`
ищет `text LIKE '%слово%'`. Ведущий шаблон не даёт воспользоваться индексом,
поэтому редкое слово — то есть ровно тот запрос, ради которого поиском и
пользуются, — читает всю таблицу целиком: замерено 0.66 с на двадцати тысячах
заданий (база 190 МБ) и растёт линейно. Частое слово отвечает мгновенно
только потому, что `LIMIT 50` останавливает перебор на пятидесятом
совпадении. Второе: результат не показывает, *где* нашлось, — список заданий
и всё, дальше человек открывает карточку и ищет глазами.
*Что даст FTS5:* поиск по индексу вместо перебора, `snippet()` с найденной
фразой в контексте и переход по щелчку на нужную секунду записи — то, ради
чего в карточку и добавлен проигрыватель. Отдельная таблица `segments_fts`
даёт заодно поиск внутри разговора.

**2. Массовые действия над выборкой в результатах.** Все действия сегодня
поштучные: `POST /jobs/{id}/retry`, `DELETE /jobs/{id}`. После обновления
модели пятьсот разговоров переобрабатываются по одному, вручную. Нужен выбор
строк в списке и действия над выборкой: повторить, удалить, сменить метку,
выгрузить одним архивом.

**3. Пик памяти на занятом сервере.** Замер делается, только когда задание в
очереди одно: счётчик `torch` общий на процесс, и при двух заданиях он не
скажет, чей пик. Значит на сервере с двумя воркерами — то есть на том, где
вопрос «хватит ли карты» и стоит, — раздел «Ресурсы» остаётся пустым.
*Что делать:* писать пик вместе с числом заданий в работе на тот момент.
«При двух заданиях карта поднималась до 27 ГБ из 32» — это и есть ответ,
нужный для планирования, и он не требует разделять память между заданиями.

**4. Выгрузка аналитики.** Отчёт только смотрят: чтобы отдать месячные числа
в бухгалтерию или руководителю, их переписывают руками. Нужна выгрузка
текущего периода в XLSX и CSV — теми же разрезами, что на экране.

**5. Сводка по расписанию.** Тревоги мониторинга срабатывают на происшествия;
отчёта, который никто не открывает, не существует. Еженедельное письмо или
вызов на адрес со сводкой (сколько сделано, что падало, как вела себя
очередь) стоит немного — приёмники и отправка уже написаны для метрик.

**6. Резервная копия по расписанию.** Сегодня это строка в `cron`, описанная
в главе «Эксплуатация», и `update.sh`, который делает копию перед
обновлением. Служебный цикл сервера уже ходит раз в час — `.backup` по
расписанию с тем же сроком хранения и командой восстановления снял бы с
администратора ещё одну ручную настройку.

#### Закрытые пункты прошлых заходов

**4. Кластеризация — сделано.** Задание захватывается одним неделимым
действием (`UPDATE ... WHERE status IN (...)`), поэтому два сервера над общей
базой берут разные задания, а не одно и то же. Экземпляр подписывает взятое
задание и обновляет отметку жизни; задания того, кто молчит дольше пяти
минут, возвращаются в очередь с записью `reclaimed`. Свои задания экземпляр
не подбирает никогда — его поток может просто грузить веса. Кто чем занят,
видно в `GET /api/queue` (поле `instances`). Подробности и требования к
раскладке — в главе «Эксплуатация».
*Проверено:* два экземпляра над одной базой — первый захватил, второй получил
отказ; задание умершего экземпляра вернулось в очередь, задание живого
осталось нетронутым.

**5. Потоковый режим выведен наружу.** Маршрут `ws://сервер/api/stream`
принимает звук кусками и отдаёт текст по ходу. Движок, который держит
состояние между кусками (Vosk), работает настоящим потоком; остальные —
скользящим окном, распознавая накопленный звук заново каждые
`stream_window_s` секунд. Режим сессия сообщает первым сообщением, а не
оставляет гадать. Формат — сырой PCM либо любой контейнер через ffmpeg.
Пример клиента: `examples/stream_microphone.py`.
*Проверено:* обмен по сокету от `ready` до `done` на демонстрационном движке
и на движке с состоянием, отказ ключу только для чтения, отказ при
выключенном `stream_enabled`, одноразовость билета.

**6. Разграничение доступа — появились подразделения и квоты.** Ключ можно
отнести к подразделению (`group`): такие ключи видят задания друг друга — то
разделение, которого не хватало трём ролям. Квоты на сутки — число заданий,
часы звука, объём файлов — считаются за скользящее окно и восстанавливаются
сами; расход виден в `GET /api/usage` **до** отказа, а не только в момент
отказа. Администратор не ограничен.
*Проверено:* коллега по подразделению видит общее задание, чужое
подразделение получает 403 и пустой список; третья загрузка при квоте в два
задания отклонена с 429 и именем параметра, который надо поднять.

**7. Кеш результатов учитывает версию модели.** В ключ кеша входит отпечаток
файлов весов — пути, размеры, время изменения. Обновились веса под тем же
именем — кеш промахнулся и задание посчиталось заново. Весов на диске нет —
отпечаток пуст, и поведение остаётся прежним.
*Проверено:* перезапись весов меняет отпечаток и ключ кеша; пустой отпечаток
даёт ровно прежний ключ.

  одной ошибки, а не «немного»: список исключений начинается с одной
  записи, а через полгода в нём десяток.
- **Развёртывание в контейнере — тем, что не требует сборки:** файлы
  Compose разбираются настоящим `docker compose config`, установка в режиме
  docker проходит целиком с подменённым `docker`, а выбор движков из
