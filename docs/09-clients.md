# Клиенты и удалённая работа

Сервер ставится один раз на машину с видеокартой, а работают с ним отовсюду: из браузера, из терминала ноутбука, из своей программы. Раздел о том, как это устроить и как не открыть при этом лишнего.

## Консольный клиент asrctl

Один файл, никаких зависимостей кроме `curl` — работает на любой Linux-машине, на macOS и в WSL. Для Windows есть эквивалент на PowerShell: `scripts/client/asrctl.ps1`.

### Профили

Адрес сервера и ключ запоминаются под именем, чтобы не повторять их в каждой команде:

```bash
asrctl config add прод https://asr.company.ru -  < ключ.txt   # ключ со стандартного ввода
asrctl config add тест http://192.168.1.50:8080                # ключ спросят, не показывая
asrctl config list
asrctl config remove тест
```

Ключ третьим словом (`config add прод адрес ah_ключ`) тоже принимается, но так он виден в списке процессов (`ps`) любому пользователю машины и остаётся в истории оболочки. Поэтому лучше «`-`» — ключ читается со стандартного ввода — или ничего: в терминале клиент спросит ключ сам, не показывая его на экране.

Профили лежат в `~/.config/asrctl/profiles` с правами 600 (на Windows — `%APPDATA%\asrctl\profiles.json`). Профиль по умолчанию — `default`; выбрать другой можно ключом `--profile` или переменной `ASRCTL_PROFILE`. `config remove` последнего профиля действительно убирает его ключ из файла — до 3.1.19 клиент отвечал «удалён», а ключ оставался; удаление профиля, которого нет, — ошибка с кодом 1.

Без профиля ключ задаётся так, по убыванию надёжности:

| Способ | Где виден ключ |
|---|---|
| `--key-file ФАЙЛ` или `ASRHUB_KEY_FILE` | нигде: читается первая строка файла |
| профиль | в `profiles` с правами 600 |
| `ASRHUB_KEY` | в окружении процесса (`/proc/<pid>/environ` — владельцу и root) |
| `--key КЛЮЧ` | в списке процессов любому пользователю машины |

Сам ключ уходит на сервер заголовком из стандартного ввода curl (`--config -`), а не аргументом — поэтому и в `ps` во время запроса его не видно.

### Отправка

```bash
# один файл, дождаться результата и скачать
asrctl --profile прод send совещание.mp3 \
    --model gigaam-v3-e2e-rnnt --formats txt,srt --wait --output ./результаты

# целый каталог, рекурсивно, низким приоритетом
asrctl send-dir ./архив --recursive --pattern '*.mp3' \
    --model gigaam-v3-ctc --formats txt,json --priority 20
```

### Наблюдение

```bash
asrctl queue --watch              # состояние очереди, обновляется на месте
asrctl list --status active       # что сейчас в работе
asrctl list --status failed -n 20
asrctl status job_7f3a9c21        # карточка задания
asrctl wait job_7f3a9c21          # ждать и скачать
```

`wait` ждёт не бесконечно: общий срок — час (`--wait-limit СЕКУНДЫ`, `0` — без ограничения, или переменная `ASRHUB_WAIT_LIMIT`). По истечении срока клиент выходит с кодом 2 и подсказкой, как проверить задание позже; само задание остаётся в очереди. Перезапуск сервера (обновление, падение службы) ожидание переживает: запрос, на который не ответили или ответили 502–504, повторяется до пяти раз подряд с паузой в пять секунд. Приостановленное задание продолжает `asrctl resume ИДЕНТИФИКАТОР`.

`--timeout` ограничивает один запрос (по умолчанию 600 с). Загрузку файла он не ограничивает — большой файл по медленной сети идёт дольше десяти минут: загрузка обрывается, только если идёт медленнее 1 КБ/с дольше двух минут.

### Результаты

```bash
asrctl get job_7f3a9c21 --format srt --output совещание.srt
asrctl get job_7f3a9c21 --format txt --output ./выгрузка/   # каталог — имя подставится
```

Клиент отличает каталог от имени файла: путь существует как каталог, заканчивается на `/`, или в последнем элементе нет точки — значит каталог. Имя, подставленное в каталог, — только имя файла с сервера, без каталогов: имя вида `../../x` из ответа сервера не уведёт результат за пределы каталога назначения.

### Коды возврата

По ним сценарии и планировщики отличают одно от другого, не разбирая текст:

| Код | Что значит |
|---|---|
| 0 | успех |
| 1 | ошибка: сервер ответил отказом (400–499, 500, 501), файл не найден, задание упало |
| 2 | неверный вызов (неизвестная команда или параметр, приоритет вне 0–100); у `wait` — вышел срок ожидания |
| 3 | сервер не ответил: неверный адрес, сеть, сервер остановлен |
| 4 | сервер или прокси временно недоступен (502, 503, 504) — например, сервер перезапускается |

Коды 3 и 4 — временные: повторить позже имеет смысл. Так и поступает `wait`.

### На Windows: asrctl.ps1

Те же команды, но параметры — в стиле PowerShell:

```powershell
.\asrctl.ps1 config add прод https://asr.company.ru -   # ключ со стандартного ввода
Get-Content ключ.txt | .\asrctl.ps1 config add прод https://asr.company.ru -
.\asrctl.ps1 send совещание.mp3 -Profile прод -Model gigaam-v3-e2e-rnnt -Formats txt,srt -Wait -Output .\результаты
.\asrctl.ps1 send-dir .\архив -Recurse -Pattern '*.mp3' -Priority 20
.\asrctl.ps1 wait job_7f3a9c21 -WaitLimitSec 7200
.\asrctl.ps1 resume job_7f3a9c21
.\asrctl.ps1 health -Server https://asr.company.ru -KeyFile C:\ключи\asr.txt
```

Клиент работает и в Windows PowerShell 5.1 (идёт в комплекте с Windows), и в PowerShell 7. Запросы он делает через `System.Net.Http`, а не через `Invoke-RestMethod`: у того в 5.1 нет `-Form`, и файл не отправлялся вовсе; ответ без указания кодировки 5.1 читает как ISO-8859-1, и кириллица превращалась в мусор; а в PowerShell 7 при ошибке терялся текст ответа сервера — 404 выглядел как «сервер недоступен». Имя файла уходит байтами UTF-8, как у браузера и curl, поэтому записи с кириллицей и запятыми в имени принимаются как есть.

Коды возврата — те же, что в таблице выше. Ключ — `-KeyFile` или `ASRHUB_KEY_FILE`; ключ с пробелом или знаком вне латиницы (частая беда скопированного из письма) отвергается сразу с кодом 2, а не превращается в «сервер недоступен». Срок ожидания — `-WaitLimitSec` или `ASRHUB_WAIT_LIMIT`; загрузка файла ограничена сроком из расчёта 128 КБ/с (не меньше `-TimeoutSec`).

### Справочники

```bash
asrctl models --language ru
asrctl models --installed             # только скачанные
asrctl health
asrctl version
```

## Работа с удалённым сервером

### По HTTPS через обратный прокси

Рабочий способ для сервера, доступного из интернета. Nginx перед приложением: он завершает TLS, ограничивает размер загрузки и пропускает WebSocket.

```nginx
server {
    listen 443 ssl http2;
    server_name asr.company.ru;

    ssl_certificate     /etc/letsencrypt/live/asr.company.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/asr.company.ru/privkey.pem;

    # Многочасовая запись — это сотни мегабайт. Умолчание nginx (1 МБ) вернёт 413.
    client_max_body_size 4096m;

    # Загрузка большого файла и распознавание идут дольше 60 секунд по умолчанию.
    proxy_read_timeout    3600s;
    proxy_send_timeout    3600s;
    proxy_request_buffering off;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Без этих трёх строк WebSocket не поднимется, и интерфейс
        # молча перейдёт на опрос — работать будет, но с задержкой.
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

Готовый файл — `docker/nginx.conf`; каждая нетривиальная директива там прокомментирована. Блок HTTPS в нём закомментирован целиком и включается раскомментированием: в нём то же, что и на порту 80, — отдельные места для WebSocket (`/ws`, `/api/stream`), ограничение метрик и мониторинга внутренней сетью, выключенная буферизация тела запроса. Переход с HTTP на HTTPS включается тремя строками в начале блока на порту 80; `/healthz` при этом остаётся на HTTP — по нему контейнер прокси проверяет сам себя.

⚠️ Три ошибки, которые стоят больше всего времени: маленький `client_max_body_size` (загрузка обрывается на 413), короткий `proxy_read_timeout` (длинное задание рвётся на середине) и забытые заголовки `Upgrade`/`Connection` (интерфейс работает, но прогресс не обновляется).

### По SSH-туннелю

Если сервер вообще не должен торчать наружу — а это правильное решение для машины с чужими записями, — доступ делается туннелем:

```bash
asrctl tunnel --host asr.company.ru --user ваш_логин
# или напрямую:
ssh -N -L 8080:127.0.0.1:8080 ваш_логин@asr.company.ru
```

Интерфейс открывается на `http://127.0.0.1:8080` вашего ноутбука. Сервер при этом слушает только `127.0.0.1` и недоступен ниоткуда, кроме как через SSH.

> **Рекомендация.** Для сервера, обрабатывающего записи разговоров, туннель предпочтительнее публичного HTTPS: он не требует сертификата, не открывает порт и пользуется той же аутентификацией, что и вход на сервер по SSH.

### Через VPN

Сервер слушает адрес внутри VPN-сети, аутентификация по ключам оставлена включённой. Разграничение по ролям (`readonly`, `user`, `admin`) работает независимо от способа доступа.

## Работа с несколькими серверами

Профили `asrctl` позволяют держать несколько серверов и переключаться между ними одним ключом. Простое распределение нагрузки — по кругу:

```bash
#!/usr/bin/env bash
# Раскладывает файлы каталога по трём серверам поочерёдно.
СЕРВЕРЫ=(сервер1 сервер2 сервер3)
i=0
for файл in ./архив/*.mp3; do
  asrctl --profile "${СЕРВЕРЫ[i % 3]}" send "${файл}" --priority 20 &
  i=$((i + 1))
  # Больше шести одновременных загрузок не даёт выигрыша — упирается в сеть.
  while [[ $(jobs -r | wc -l) -ge 6 ]]; do wait -n; done
done
wait
```

Для серьёзного распределения нагрузки лучше поставить общий балансировщик перед несколькими экземплярами, а базу и каталог результатов вынести на общее хранилище.

## Интеграция в свои программы

Полное описание HTTP-интерфейса — [08. Программный интерфейс](08-api.md). Коротко о выборе способа получить результат:

| Способ | Когда подходит |
|---|---|
| Опрос `GET /api/jobs/{id}` | скрипт, разовая задача, до нескольких заданий |
| Webhook | постоянно работающий сервис с доступным адресом |
| WebSocket | интерфейс, показывающий прогресс в реальном времени |

Опрос в цикле для сервиса, обрабатывающего тысячи файлов, — самая частая ошибка интеграции: он создаёт нагрузку, растущую с числом заданий, и всё равно узнаёт о завершении с задержкой.

## Обработка файлов на удалённой машине без загрузки

Если файлы уже лежат на сервере (например, автоматически складываются туда системой записи), гонять их через сеть незачем. Запустите обработку прямо на сервере:

```bash
ssh сервер 'cd /opt/asrhub && \
  for f in /данные/записи/*.mp3; do
    scripts/client/asrctl send "$f" --server http://127.0.0.1:8080 --priority 20
  done'
```

Или заведите на сервере периодическую задачу, которая забирает новые файлы из каталога:

```bash
# /etc/cron.d/asrhub-watch — каждые пять минут
*/5 * * * * asrhub /opt/asrhub/scripts/client/asrctl send-dir /данные/входящие \
    --pattern '*.mp3' --priority 20 --move-to /данные/отправленные \
    >> /var/log/asrhub-watch.log 2>&1
```

`--move-to` уносит отправленный файл в указанный каталог (с тем же путём внутри), и следующий запуск его уже не видит. Файл, который отправить не удалось, остаётся на месте и уйдёт в следующий раз. На Windows то же — `-MoveTo`.

Без `--move-to` повторный запуск не безопасен, хотя и не пересчитывает записи заново: дедупликация по содержимому отдаёт готовый результат из кеша, но каждый раз заводит задание-копию, копирует каталог результатов и тратит суточную квоту. Каждые пять минут на каждый файл каталога — это тысячи лишних заданий за день.

## Примеры на Python

В каталоге `examples/` лежат пять разобранных примеров. Каждый запускается
сам по себе и написан так, чтобы его читали, а не только выполняли:
комментарии объясняют, почему сделано именно так.

```bash
export ASRHUB_SERVER=http://сервер:8080
export ASRHUB_KEY="$(cat /var/lib/asrhub/api-key.txt)"
pip install requests websockets websocket-client
```

| Файл | Что показывает |
|---|---|
| `transcribe.py` | Простейший случай: поставить файл, дождаться, забрать текст. Заодно — как разбирать ответ об ошибке |
| `batch_folder.py` | Каталог целиком: ограничение одновременных отправок, отказ по одному файлу не останавливает остальные, состояние снимается одним облегчённым запросом на всю пачку |
| `live_events.py` | Подписка на события вместо опроса, с одноразовым билетом вместо ключа в адресе |
| `monitoring_pull.py` | Снимок метрик со сверкой по порогам из справочника — полезно, когда своей системы наблюдения ещё нет |
| `stream_microphone.py` | Распознавание на лету: звук кусками по WebSocket, черновик и закреплённые фразы по ходу речи; без микрофона «наговаривает» готовый файл |

## Сравнительный прогон на своих записях

Числа в главе «Сравнение моделей» взяты из публикаций авторов и с открытых
наборов. На вашем звуке и вашем оборудовании они будут другими, иногда в
разы, поэтому единственный честный способ выбрать модель — прогнать её на
своих записях:

```bash
python3 benchmarks/run.py ./эталон --models gigaam-v3-e2e-rnnt,faster-whisper-large-v3
python3 benchmarks/run.py ./эталон --reference ./эталон/тексты   # посчитается и WER
```

Сценарий отбрасывает первый прогон (в него входит загрузка весов), считает
средние и медианы и кладёт результат в `benchmarks/` — файлом JSON
(`generated_at`, `host`, `platform`, `files` и `results`: по модели — средний
и срединный RTF, уверенность, WER, часы звука и счёта и `runs` с каждой
записью) и сводной таблицей в Markdown. Адрес и ключ — те же `ASRHUB_SERVER`
и `ASRHUB_KEY`, что у примеров.
Условия честного замера описаны в `benchmarks/README.md`: не меньше двадцати
записей, свой звук, эталонные тексты, одна модель за раз.
